## 这份表怎么用

这份术语表是给你**边读边查**用的，不是拿来背的。遇到正文里一个眼熟但说不清的词，回到这里看一眼"它是干什么用的"，然后回去继续读。

**为什么一定要中英对照？** 因为中文资料和英文原文常常不是一套词：

- 同一个概念，不同中文译法并存。比如 Sharding 有人叫"分片"，有人叫"分区"；Cache-Aside 有人叫"旁路缓存"，有人叫"旁路模式"，还有人直接叫"懒加载"。你只记住中文名，搜索时会漏掉一大半资料。
- 同一个中文词，可能对应完全不同的英文。比如"一致性"在 CAP 里是 Consistency，在 ACID 里也是 Consistency，但两者说的根本不是一回事；"分区"在数据库里是 Sharding，在网络里是 Network Partition。
- 一手资料几乎都是英文。Kafka 官方文档、Raft 论文、AWS 白皮书、Prometheus 文档——想深挖任何一块，都得用英文名去搜。

所以本表的用法是：**先用中文名定位，再用英文名去搜原文**。

几点说明：

- 每个术语给的是"它是干什么用的"，不是同义词翻译。看不懂解释时，去对应章节看完整上下文。
- 分组只是方便查找，很多术语跨组。比如 Quorum 既在"存储与数据库"里出现，也在"分布式协调"里出现。
- 表格里放不下的**易混淆术语**，会单独用引用块展开对比，这些往往是面试里最容易被追问的点，建议重点看。

## 1. 基础与架构

| 回滚 | Rollback | 出问题时把变更退回到之前的状态。 |

### 易混淆：限流算法的四种写法

> **固定窗口计数器（Fixed Window Counter）**：把时间切成固定的分钟/秒格子计数。实现最简单，但格子边界会放过两倍流量。
> **滑动窗口日志（Sliding Window Log）**：记录每个请求的时间戳，精确但内存开销大。
> **滑动窗口计数器（Sliding Window Counter）**：用"上一格 + 当前格"按比例加权估算，是精度和开销的折中。
> **令牌桶（Token Bucket）**：以固定速率往桶里放令牌，请求要拿令牌才能过。**允许突发**，是业界最常用的方案。
> **漏桶（Leaky Bucket）**：请求先入队，再以恒定速率流出。**不允许突发**，输出绝对平滑。
>
> 一句话记法：**令牌桶管"平均速率 + 允许突发"，漏桶管"输出绝对匀速"**。

### 易混淆：本地限流 vs 全局限流

> **本地限流（Local Rate Limit）**：每台服务器各自计数。实现简单，但 N 台机器实际总配额是 N 倍，配额不准。
> **全局限流（Global Rate Limit）**：把计数集中到 Redis 等共享存储。配额准确，但每次请求都要访问共享存储，多了一次网络往返，且共享存储本身可能成为瓶颈。
>
> 工程上的常见做法是**分层**：本地限流挡住绝大部分突发，全局限流做最终兜底。

### 易混淆：写扩散 vs 读扩散

> **写扩散 / 推（Fan-out on Write）**：用户发一条内容时，立刻把它写进所有粉丝的收件箱。读的时候直接读自己的收件箱，**读很快，写很贵**。
> **读扩散 / 拉（Fan-out on Read）**：发内容时只写一份，读的时候再去拉所有关注对象的内容合并。**写很便宜，读很贵**。
>
> 大 V 问题是分水岭：一个有几千万粉丝的明星发一条动态，写扩散要写几千万次，系统直接被打爆。所以真实系统常用**混合策略**——普通用户走写扩散保证读体验，大 V 走读扩散避免写风暴，读取时再把两路结果合并。

### 易混淆：耐久性 vs 可用性

> **耐久性（Durability）**：数据**不丢**。对象存储常喊"11 个 9"，指的是存进去的数据几乎不可能永久丢失。
> **可用性（Availability）**：服务**能用**。通常"4 个 9"，指的是请求能得到响应的时间比例。
>
> 两者互不保证。一个系统可以数据永不丢失但整整一天无法访问（可用性差、耐久性好），也可以随时能读写但偶尔丢数据（可用性好、耐久性差）。对象存储的答案通常是：**用纠删码 + 多副本把耐久性做到极致，用多机房冗余把可用性做到四个九**。

### 易混淆：四种存储语义

> **Cache-Aside（旁路缓存）**：应用自己管缓存，读时先查缓存、未命中再查库并回填。最常用。
> **Read-Through（读穿透）**：缓存组件自己负责回源，应用只和缓存打交道。
> **Write-Through（写穿透）**：写的时候同步写缓存和数据库，缓存永远和库一致，但写变慢。
> **Write-Back（写回）**：只写缓存，之后异步刷回数据库，写最快，但宕机会丢数据。
>
> 记忆要点：**穿透是同步（安全但慢），写回是异步（快但可能丢）**。

## 3. 缓存

| 中文名 | 英文名 | 一句话解释 |
|---|---|---|
| 缓存 | Cache | 把慢存储里的热点数据放到快存储，用空间换时间。 |
| 缓存命中 / 未命中 | Cache Hit / Miss | 请求在缓存里找到 / 没找到数据。 |
| 缓存命中率 | Hit Rate | 命中次数占总请求的比例，直接决定缓存的价值。 |
| 旁路缓存 | Cache-Aside | 应用自己管缓存：读时先查缓存，未命中再查库并回填。最常用。 |
| 读穿透 | Read-Through | 缓存组件自己负责回源，应用只和缓存打交道。 |
| 写穿透 | Write-Through | 写时同步更新缓存和数据库，一致性最好但写变慢。 |
| 写回 | Write-Back | 只写缓存，之后异步刷回数据库，写最快但宕机可能丢数据。 |
| 写旁路 | Write-Around | 写的时候绕过缓存直接写库，避免写了却不会被读的数据污染缓存。 |
| 缓存失效 | Invalidation | 数据变了之后让旧缓存不再被使用。 |
| 过期时间 | TTL（Time To Live）| 给缓存设一个存活时长，到期自动失效。 |
| 淘汰策略 | Eviction Policy | 缓存满了之后决定先踢掉谁的规则。 |
| 最近最少使用 | LRU（Least Recently Used）| 踢掉最久没被访问的那个，适合有明显时间局部性的场景。 |
| 最不经常使用 | LFU（Least Frequently Used）| 踢掉访问次数最少的那个，适合长期热点，但对新数据不友好。 |
| 先进先出 | FIFO（First In First Out）| 按进入顺序淘汰，最简单但完全不管访问频率。 |
| 缓存穿透 | Cache Penetration | 查一个**根本不存在**的数据，缓存和数据库都没命中，请求每次都打到数据库。 |
| 缓存击穿 | Cache Breakdown | 某个**热点 key 突然过期**，瞬间大量请求同时打到数据库。 |
| 缓存雪崩 | Cache Avalanche | **大批 key 同时过期**，或者缓存集群整体宕机，数据库被瞬间压垮。 |
| 惊群 | Thundering Herd | 大量请求同时发现缓存失效，一起冲向后端。 |
| 空值缓存 | Null Caching | 把"查不到"也缓存起来（短 TTL），用于防穿透。 |
| 布隆过滤器预检 | Bloom Filter Pre-check | 查询前先用布隆过滤器挡掉肯定不存在的 key，用于防穿透。 |
| 缓存预热 | Cache Warming | 上线或扩容后提前把热点数据加载进缓存，避免冷启动被打穿。 |
| 缓存一致性 | Cache-DB Consistency | 让缓存和数据库的数据保持一致的策略总称。 |
| 延迟双删 | Delayed Double Delete | 更新库后先删缓存，隔一小段时间再删一次，兜住并发读到旧值的窗口。 |
| 双写 | Double Write | 同时写缓存和数据库，简单但容易不一致。 |
| 计数器缓存 | Counter Cache | 把点赞数、阅读数这类高频计数放缓存里累加。 |
| 内容缓存 | Content Cache | 缓存静态内容（图片、HTML），通常放在 CDN 层。 |
| 单飞 | Singleflight | 同一个 key 的并发未命中只放一个请求去回源，其余等待复用结果。 |
| 多级缓存 | Multi-level Cache | 本地缓存 + 分布式缓存分层，兼顾速度和容量。 |
| 一致性哈希环 | Consistent Hash Ring | 缓存节点按哈希环分布，加减节点时只影响相邻区间。 |

### 易混淆：缓存穿透 vs 击穿 vs 雪崩（必看）

> 三个词都描述"请求绕过缓存打到数据库"，但**触发原因和范围完全不同**：
>
> | | 触发原因 | 范围 | 典型解法 |
> |---|---|---|---|
> | **穿透（Penetration）** | 查的数据**压根不存在** | 单个（或一批伪造的）不存在的 key | 空值缓存、布隆过滤器、参数校验 |
> | **击穿（Breakdown）** | **单个热点 key** 恰好过期 | 单个热点 key | 互斥锁重建、逻辑过期、热点永不过期 |
> | **雪崩（Avalanche）** | **大批 key 同时过期**，或缓存整体故障 | 全库 / 全集群 | 过期时间加随机抖动、多级缓存、熔断降级 |
>
> 一句话区分：**穿透是"数据不存在"，击穿是"一个热点过期"，雪崩是"一批同时过期或缓存整个挂了"**。
> 另外注意击穿和惊群（Thundering Herd）常被混用：击穿强调"热点 key 失效"这个**原因**，惊群强调"大量请求同时冲向后端"这个**现象**，二者经常同时出现。

### 易混淆：LRU vs LFU

> **LRU（最近最少使用）**：看"多久没被访问"。刚被访问过的数据排在最前，淘汰队尾。
> **LFU（最不经常使用）**：看"总共被访问了多少次"。累计次数少的先淘汰。
>
> 差别在"突发的旧数据"上：LRU 会把一个刚刚被扫过一次的冷数据放到队首，把真正的热点挤出去（缓存污染）；LFU 则不会，但**新加入的热数据因为次数少，很容易被误杀**（需要额外的计数衰减或新数据保护机制）。
> 工程上常把两者结合，例如 Redis 的近似 LRU，以及各类"LRU + 频率"的混合策略。

## 4. 一致性理论

| 中文名 | 英文名 | 一句话解释 |
|---|---|---|
| CAP 定理 | CAP Theorem | 网络分区发生时，一致性和可用性只能二选一。 |
| PACELC | PACELC | CAP 的补充：没分区时（E），还要在延迟（L）和一致性（C）之间权衡。 |
| 分区容错 | Partition Tolerance | 网络分区（节点间通信中断）时系统仍能继续运行。 |
| 一致性（CAP 中的） | Consistency | 所有节点在同一时刻看到相同的数据。 |
| 可用性（CAP 中的） | Availability | 每个请求都能在有限时间内得到非错误响应。 |
| 强一致性 | Strong Consistency | 写入成功后，任何后续读取都能看到这次写入。 |
| 弱一致性 | Weak Consistency | 写入后不保证何时能被读到。 |
| 最终一致性 | Eventual Consistency | 停止写入后，经过一段时间所有副本最终会收敛到相同值。 |
| 线性一致 | Linearizability | 最强的一致性：整个系统表现得像只有一份数据，且操作按真实时间排序。 |
| 顺序一致 | Sequential Consistency | 所有节点看到相同的操作顺序，但不要求和真实时间一致。 |
| 因果一致 | Causal Consistency | 有因果关系的操作保持顺序，无因果的可以乱序。 |
| 读己之写 | Read-Your-Own-Writes | 用户总能看到自己刚才写入的数据。 |
| 单调读 | Monotonic Reads | 用户不会读到比之前更旧的数据（不会"时光倒流"）。 |
| ACID | ACID | 事务的四个保证：原子性、一致性、隔离性、持久性。 |
| 原子性 | Atomicity | 事务里的操作要么全做，要么全不做。 |
| 一致性（ACID 中的） | Consistency | 事务前后数据都满足业务约束（和 CAP 的 C 不是一回事）。 |
| 隔离性 | Isolation | 并发事务之间互不干扰，仿佛串行执行。 |
| 持久性 | Durability | 事务提交后，即使宕机数据也不会丢。 |
| 隔离级别 | Isolation Level | 在并发正确性和性能之间选择的档位。 |
| 读已提交 | Read Committed | 只能读到已提交的数据，是多数数据库的默认级别。 |
| 可重复读 | Repeatable Read | 同一事务内多次读同一行结果相同。 |
| 快照隔离 | Snapshot Isolation | 事务读的是开始那一刻的数据库快照。 |
| 串行化 | Serializable | 最强的隔离级别，效果等同串行执行，但并发度最低。 |
| BASE | BASE | 基本可用、软状态、最终一致，是对 ACID 的松绑。 |
| 基本可用 | Basically Available | 允许牺牲部分功能或延迟，但保证核心可用。 |
| 软状态 | Soft State | 允许中间状态存在，不要求时刻一致。 |
| 版本向量 | Version Vector | 用每个节点的版本号组合，判断两个副本的因果关系。 |
| 向量时钟 | Vector Clock | 版本向量的经典实现，用于检测并发写冲突。 |
| 最后写入者胜 | LWW（Last-Write-Wins）| 冲突时直接取时间戳最新的那个，简单但会丢写。 |
| 冲突解决 | Conflict Resolution | 多副本写入冲突时决定保留哪个值的规则。 |
| 收敛 | Convergence | 不再有新写入后，所有副本最终变成相同状态。 |

### 易混淆：强一致 vs 线性一致 vs 最终一致

> - **最终一致（Eventual Consistency）**：最弱。"现在可能读到旧的，但迟早会一致"。适合点赞数、粉丝数这类可以短暂不准的数据。
> - **强一致（Strong Consistency）**：写入成功后立刻能读到新值。但"立刻"的定义可以很模糊。
> - **线性一致（Linearizability）**：最强，也是最严格的定义。要求整个系统**表现得像只有一份数据**，并且操作顺序和真实物理时间一致。任何读到"还没发生的写"或"已经过去的旧值"都算违反。
>
> 关系是：**线性一致 ⊂ 强一致 ⊂ 最终一致**（越往后越宽松）。面试里说"我们要强一致"通常太笼统，能说清"要线性一致还是只要读己之写"才是加分项。

### 易混淆：ACID 的 C vs CAP 的 C

> 两个 C 长得一样，含义完全不同：
>
> - **ACID 的 Consistency**：指**业务约束不被破坏**。比如转账前后总金额不变。这是应用层的语义，数据库只是保证事务不会把它搞坏。
> - **CAP 的 Consistency**：指**多个副本看到同一份数据**。这是分布式系统层面的语义。
>
> 看到 "C" 先问一句：这是在讲事务，还是在讲多副本？

## 5. 分布式协调

| 中文名 | 英文名 | 一句话解释 |
|---|---|---|
| 共识算法 | Consensus Algorithm | 让多个节点对同一个值达成一致的算法，是分布式系统的地基。 |
| Raft | Raft | 以易理解著称的共识算法，用强领导者 + 日志复制实现一致性。 |
| Paxos | Paxos | 最早的共识算法，理论优美但工程实现困难。 |
| Zab | Zab | ZooKeeper 使用的原子广播协议。 |
| 多数派 | Majority / Quorum | 超过一半的节点，任意两个多数派必有交集，这是共识的基础。 |
| 领导者选举 | Leader Election | 节点们选出唯一的主节点来协调写入。 |
| 任期 | Term | Raft 里的逻辑时间单位，每选一次主就加一。 |
| 日志复制 | Log Replication | 主节点把操作日志复制到多数派，然后才提交。 |
| 心跳 | Heartbeat | 主节点周期性发信号证明自己还活着，超时则触发重新选举。 |
| 租约 | Lease | 给主节点一段有期限的授权，到期自动失效，避免脑裂。 |
| 脑裂 | Split Brain | 网络分区导致出现两个都以为自己是主的节点，可能造成数据分叉。 |
| 网络分区 | Network Partition | 节点之间网络断开，被切成互不可见的几组。 |
| 协调服务 | Coordination Service | 专门提供选主、配置、分布式锁等能力的服务。 |
| ZooKeeper | ZooKeeper | 经典的协调服务，Kafka 早期依赖它管理元数据和选主。 |
| etcd | etcd | 基于 Raft 的键值协调服务，Kubernetes 用它存集群状态。 |
| KRaft | KRaft | Kafka 内置的 Raft 实现，用来取代 ZooKeeper。 |
| FLP 不可能性 | FLP Impossibility | 在完全异步的系统中，只要有一个节点可能故障，就不存在既保证安全又保证活性的共识算法。 |
| 两将军问题 | Two Generals Problem | 通信不可靠时，双方无法 100% 确认对方也确认了，说明"完全一致"做不到。 |
| 时钟偏移 | Clock Skew | 不同机器的时钟走得不一样，所以不能只靠物理时间排序。 |
| 逻辑时钟 | Logical Clock | 用计数器而非物理时间表达事件先后。 |
| 单调时钟 | Monotonic Clock | 只会前进不会回拨的时钟，用于测量时间间隔。 |
| 分布式锁 | Distributed Lock | 跨进程互斥的锁，通常靠协调服务或 Redis 实现。 |
| 领导者-跟随者 | Leader-Follower | 一个主节点处理写，其余跟随并复制。 |
| 状态机复制 | State Machine Replication | 只要所有节点按相同顺序执行相同命令，状态就必然一致。 |
| 全局有序 | Total Order | 所有节点对事件顺序的看法完全一致。 |
| 提交索引 | Commit Index | Raft 中已确认被多数派复制的日志位置。 |

### 易混淆：2PC / 3PC / TCC / Saga

> 这四个都是"跨多个服务 / 分片完成一件事"的方案，区别在**一致性强度**和**可用性代价**：
>
> | 方案 | 思路 | 一致性 | 主要问题 |
> |---|---|---|---|
> | **2PC（两阶段提交）** | 协调者先让所有参与者"准备"，全票通过再"提交" | 强一致 | 同步阻塞、协调者单点、参与者长时间持锁 |
> | **3PC（三阶段提交）** | 在 2PC 前加一个"CanCommit"预询问 | 稍弱，减少阻塞 | 仍然解决不了网络分区下的不一致，实际很少用 |
> | **TCC（Try-Confirm-Cancel）** | 业务层面预留资源（Try），再确认（Confirm）或取消（Cancel） | 最终一致 | 需要为每个操作写三个接口，业务侵入大 |
> | **Saga** | 把长事务拆成一串本地事务，失败就反向执行补偿操作 | 最终一致 | 没有隔离性，中间状态对外可见，补偿逻辑难写 |
>
> 一句话选择：**要强一致且能接受阻塞 → 2PC；要高可用、能接受最终一致 → TCC 或 Saga**。3PC 基本只出现在教材里。
> 另外 TCC 里有三个经典坑要特别小心：**空回滚**（Try 没执行但收到 Cancel）、**悬挂**（Cancel 先到，Try 后到）、**幂等**（Confirm / Cancel 被重复调用）。

### 易混淆：at-most-once / at-least-once / exactly-once

> 三者描述的是**消息在"生产者 → broker → 消费者"整条链路上被处理的次数**：
>
> - **至多一次（At-Most-Once）**：先标记已读，再处理。**可能丢消息，但绝不重复**。适合日志采集这类丢了也不心疼的场景。
> - **至少一次（At-Least-Once）**：先处理，成功后再确认。**绝不丢，但可能重复**。绝大多数消息队列的默认语义，代价是消费端必须自己处理重复。
> - **恰好一次（Exactly-Once）**：听起来最理想，但**跨网络无法真正实现**——因为确认消息本身可能丢失，发送方永远无法区分"对方没收到"和"对方收到了但确认丢了"（这正是两将军问题）。
>
> 工程上的"恰好一次"其实是两件事拼出来的：**至少一次投递 + 消费端幂等**，也就是常说的**有效一次（Effectively-once）**。
> 面试里的正确说法是：**"跨网络的严格恰好一次做不到，我们做的是至少一次加幂等去重，效果上等价于恰好一次。"** 直接说"我们用 exactly-once 保证不重复"会被追问到底。

### 易混淆：事件时间 vs 处理时间

> - **事件时间（Event Time）**：这条数据**在现实世界发生的时刻**，比如用户点击按钮的那一秒。由数据自己带着。
> - **处理时间（Processing Time）**：**系统处理到这条数据**的时刻。由机器时钟决定。
>
> 为什么必须区分？因为网络延迟和重试会让两者错开很远。用处理时间做"每分钟点击量"，会把延迟到达的数据算到错误的分钟里，结果完全失真。
>
> 代价是：用事件时间就必须处理**乱序**和**迟到**——这就是**水位线（Watermark）**和**允许迟到（Allowed Lateness）**存在的原因。水位线是"我认为某时刻之前的数据都到齐了"的进度信号，它决定了窗口什么时候可以安全输出结果。

### 易混淆：推 vs 拉

> - **推（Push）**：broker 主动把消息送给消费者。**延迟低**，但 broker 必须知道消费者的处理能力，否则容易把慢消费者压垮。
> - **拉（Pull）**：消费者主动来取。**消费者自己控制节奏**，天然支持批量和回溯，代价是没数据时会空轮询浪费资源。
>
> 解决空轮询的办法是**长轮询（Long Polling）**：没数据时请求先挂起，有数据或超时才返回。Kafka 消费者用的就是长轮询。

>
> 一个查数据，一个取图片。另外 GeoHash 有一个必须知道的缺陷：**它是"前缀相同 ⇒ 位置相近"的单向保证，反过来不成立**——两个物理上很近的点可能被分到相邻但前缀完全不同的格子里（边界问题）。所以查询时**必须连同周围 8 个格子一起查**，只查自己所在的格子会漏结果。

| 行情发布器 | Market Data Publisher | 把撮合结果广播给所有市场参与者的组件。 |
| K 线图 | Candlestick | 用开盘、收盘、最高、最低四个价格描述一段时间行情的图表。 |

### 易混淆：复式记账 vs 单纯改余额

> 初学者最容易写出的支付逻辑是"用户余额减 100，商户余额加 100"。这有两个致命问题：**中间任何一步失败，钱就凭空消失或凭空产生**；而且**没有任何记录能证明账目对不对**。
>
> 复式记账的做法是：每笔交易同时产生一条借方和一条贷方分录，**所有分录的借贷总额永远相等**。这样任何时刻都能做一次全局校验——如果借贷不平衡，就一定出了问题。
>
> 一句话记法：**改余额只记录"结果"，复式记账记录"因果"，并且自带对账能力**。

| 中文名 | 英文名 | 一句话解释 |
