# 高频面试题速查手册

> 本手册汇总 28 章的核心考点，供面试前快速复习。
> 每章详细论述见对应章节正文。

---

## 一、通用答题框架

**核心认知**：系统设计面试是一场「协作模拟（Collaboration Simulation）」，不是考试。45 分钟不可能设计出真实系统，面试官看的是你的**思考过程、沟通能力、技术取舍**——**说不出来就等于没有**。

| 步骤 | 时间 | 必做动作 | 产出物 |
|---|---|---|---|
| **Step 1 理解问题、划定范围** | 3~10 分钟 | 问 4 类问题（核心功能 / 规模 / 客户端形态 / 已有约束）；把 5~8 行假设**写在白板上**并请面试官纠正 | 需求与假设清单 |
| **Step 2 高层设计 + 取得认可** | 10~15 分钟 | 画方框图（客户端 / API / 数据库 / 缓存 / CDN）；**每画 2~3 个组件就停下来确认**；估算用「数字 → 结论 → 组件」三段式；走查核心用例找边界 | 方框图 + API 定义 + 粗略估算 |
| **Step 3 深入设计** | 10~25 分钟 | 挑 1~2 个关键组件深挖；**主动**提瓶颈和解法；控制细节颗粒度 | 关键组件详设 + 瓶颈分析 |
| **Step 4 收尾** | 3~5 分钟 | 主动指出瓶颈与扩展策略；复述 2~3 个核心决策与取舍；提改进方向（扩 10 倍怎么办 / 故障怎么办） | 一段总结 + 2~3 个改进方向 |

**三条黄金原则**

1. **先问再做**——表结构是结论不是起点；不澄清需求就画图，很可能解错题。
2. **持续沟通**——沉默超过 15 秒就开口，哪怕只是「我在想存储方案」。
3. **80% 的时间花在 20% 的关键点上**——平均用力等于没有深度。

**深入什么？优先级**：① 面试官主动追问的 → ② 你的核心创新点 → ③ 规模带来的瓶颈 → ④ 你最熟的技术。

**细节讲不讲？判断标准**：**这个细节能否改变设计结论**？能则讲，不能则一句话带过。

**收尾最高级形态**：主动说「我这个设计在 X 场景下会退化」——面试官招的是同事，不是完美答案。

## 二、必须能脱口而出的 15 个数字

| 数字 | 含义 | 出处 |
|---|---|---|
| 1 天 ≈ 10^5 秒 | 容量估算的基准换算（真实 86,400，偏低 13.6% 但心算秒出） | 第 2 章 |
| 内存 ~100 ns / NVMe SSD ~50 µs / HDD 寻道 ~10 ms | 延迟相对倍数：1× / 500× / 10 万×；一次内存访问换掉一次磁盘访问收益几百倍 | 第 2 章 |
| 跨洲 RTT 100~200 ms；光纤光速 200 km/ms | 跨洲延迟有物理下限，CDN 是唯一解 | 第 2 章 |
| 4 × 99.9% 串联 = 99.6% | 串联可用性**相乘**；99.9% 月停 43.2 分钟 | 第 2 章 |
| `N/(N+1)` → `1/N` | 取模哈希的迁移比例 → 一致性哈希的迁移比例（3→4 台 75%） | 第 5 章 |
| 相对标准差 ≈ `1/√V` | 虚拟节点数 V 决定分布均匀度（V=64→12.5%，V=256→6.25%） | 第 5 章 |
| `W + R > N` | Quorum 强一致判据（N=3、W=R=2 最常用） | 第 6 章 |
| Snowflake：409.6 万/秒、1024 台、41 位 ≈ 69.7 年 | 1 位符号 + 41 位毫秒 + 5 位数据中心 + 5 位机器 + 12 位序列 | 第 7 章 |
| `62^7 ≈ 3.52 万亿`（`62^6 ≈ 568 亿`） | 7 位短码容量 > 3650 亿条记录，6 位不够 | 第 8 章 |
| 10 亿 URL / 1% 误判 ≈ 1.2 GB | 布隆过滤器（Bloom Filter）的内存成本 | 第 9 章 |
| GeoHash 6 位 ≈ 1.22 km × 0.61 km | 赤道处精度；共 12 个精度层级 | 第 16 章 |
| 面积尺度因子 `1/cos²φ`；瓦片总数 `4^Z` | Web Mercator 等角不等积；Z=21 约 4.4 万亿块瓦片 | 第 18 章 |
| CH / CRP 加速 500~1000 倍 | 导航预处理加速（Dijkstra 经济上不成立） | 第 18 章 |
| Redis ZSET：2500 万成员 ≈ 3 GB，1 亿 ≈ 13 GB，`ZRANK` ≈ 5 µs | 排行榜的瓶颈是内存与单点，不是算法 | 第 25 章 |
| 1000 万序列 → 100 万点/秒 → 约 170 GB/天 | 监控系统写入量倒推（10 秒采集间隔、每点压缩后约 2 字节） | 第 20 章 |

## 三、按主题的核心考点

### 3.1 基础与架构（第 1–3 章）

**第 1 章 · Scaling（水平扩展）**
- **一句话定位**：系统随用户规模增长而演化的标准路径，以及每一步引入的新组件和技术债。
- **必答**：① Web 层**无状态化**是水平扩展前提（session 外置 Redis）；② 数据库**有状态**，是真正的瓶颈，解法是复制（读）+ 分片（写/存储）；③ 缓存是「用一致性换性能」，必须配套失效、穿透防护、降级。
- **追问**：Q「主库挂了怎么保证不丢数据？」→ A 半同步复制 + GTID 定位切换位点 + 自动故障转移把 RTO 压到秒级；RPO=0 需同步复制，代价是写延迟上升。

**第 2 章 · Back-of-the-Envelope Estimation（粗略估算）**
- **一句话定位**：60 秒内用纸笔判断系统规模与瓶颈，产物不是精确数字，而是**一组设计决策**。
- **必答**：① **先写假设再计算**，并念给面试官听；② 1 天 ≈ 10^5 秒；③ 读 QPS 通常远大于写 QPS，两个都算；④ 存储 = 日增量 × 保留天数 × **副本数**；⑤ 最后把数字**翻译成结论**。
- **追问**：Q「为什么用 10^5 而不是 86400？」→ A 假设误差远大于这 13.6%，且 10^5 让除法退化成小数点移位，紧张环境下更不易错。

**第 3 章 · System Design Framework（面试框架）**
- **一句话定位**：把开放问题变成可执行动作的四步协作流程（见 §一）。
- **必答**：① 先问再做，写假设；② 每画几个组件停下确认（Get Buy-In）；③ 估算服务于选型；④ 深入要挑重点并主动提瓶颈；⑤ 收尾总结取舍、提改进、说不足。
- **追问**：Q「时间不够砍哪部分？」→ A 砍深入设计里优先级最低的点，**绝不砍 Step 1 和 Step 4**。

### 3.2 核心组件（第 4–7 章）

**第 4 章 · Rate Limiter（限流器）**
- **一句话定位**：关键路径上按维度限制速率的保护层，难点在**分布式原子性**与**故障降级**。
- **必答**：① 五种算法——令牌桶（通用首选，支持突发）、漏桶（强制匀速）、固定窗口（简单但有边界突刺）、滑动窗口日志（精确但费内存）、滑动窗口计数器（工业最常用）；② 存储用 Redis（状态可丢，不必持久化）；③ `读 → 判断 → 写` 必须原子，用 **Lua 脚本**；④ 被限流返回 429 + `X-RateLimit-*` + `Retry-After`。
- **追问**：Q「限流器自己挂了怎么办？」→ A 默认 **fail-open**（保护层不该成为新单点）；登录/验证码/支付 **fail-closed**；生产用 fail-open + 本地内存兜底 + 告警。

**第 5 章 · Consistent Hashing（一致性哈希）**
- **一句话定位**：把哈希空间首尾相接成环，key 归属顺时针第一个节点，迁移比例从 `N/(N+1)` 降到 `1/N`；**必须配虚拟节点**才能均匀。
- **必答**：① 问题起点是取模哈希在 N 变化时缓存大面积失效；② 添加节点从**顺时针后继**接管区间，移除节点把区间交给**顺时针后继**；③ 虚拟节点让相对标准差从 100% 降到约 `1/√V`（常见 64~256）；④ 边界：**只决定映射关系，不搬数据，也不解决热 key**。
- **追问**：Q「移除一台服务器，数据去哪？」→ A 交给它的**顺时针后继**（不是逆时针前驱）。

**第 6 章 · Key-Value Store（键值存储）**
- **一句话定位**：去中心化、可调一致性、高可用的分布式 KV——一致性哈希分片 + 多副本 + Quorum + 向量时钟 + Merkle 树。
- **必答**：① CAP 的准确表述：**P 必选**，实际在 C 和 A 间取舍，CA 不存在；② `W + R > N` 保证强一致（鸽巢原理，读写集合必相交），N=3、W=R=2 最常用；③ 冲突检测用**向量时钟**——检测归系统，解决归业务；④ 故障三件套：Gossip 检测、Sloppy Quorum + Hinted Handoff、Merkle 树反熵。
- **追问**：Q「N=3 时挂了两台还能服务吗？」→ A 看 W/R。W=2、R=2 时只剩 1 台无法满足法定人数，写入失败——这正是 CP 系统的表现。

**第 7 章 · Unique-Id Generator（唯一 ID 生成器）**
- **一句话定位**：生成 64 位、全局唯一、按时间有序 ID，核心方案是 Snowflake 的位编码。
- **必答**：① 自增主键失效的根本原因是单点串行发号；② 四方案对比——多主复制（无序）、UUID（128 位且无序）、票据服务器（单点）、Snowflake（综合最优但有机器上限与时钟依赖）；③ 时钟回拨是**正确性问题**，短回拨自旋等待、长回拨抛异常 + 告警；④ ID 有序的价值在数据库索引（InnoDB 聚簇索引尾部追加 vs 页分裂）。
- **追问**：Q「Snowflake 机器不够用怎么办？」→ A 重分配位段，或改用**号段模式**（Leaf-segment，从中心批量领取）。

### 3.3 经典题型（第 8–15 章）

**第 8 章 · URL Shortener（短链服务）**
- **一句话定位**：唯一 ID + Base 62 编码生成短码，缓存扛读、分片扛存储。
- **必答**：① 量级：3650 亿条、约 365 TB、平均写 1,157 QPS、读 11,574 QPS；② 两套方案——Base 62（无碰撞、可被枚举）vs 哈希 + 冲突解决（固定长度、不可预测）；③ 碰撞三层：布隆过滤器预检 → 唯一索引兜底 → 重试（有上限）；④ 读路径先查缓存（读是写的 10 倍且分布极不均匀）。
- **追问**：Q「为什么不用 301？」→ A 301 被浏览器永久缓存，导致无法统计点击、无法改目标、**无法撤销恶意链接**。

**第 9 章 · Web Crawler（网络爬虫）**
- **一句话定位**：把「下载」和「调度」分离，用双层 URL Frontier 同时实现优先级和礼貌性。
- **必答**：① 量级：10 亿页/月 → 平均约 400 QPS、峰值约 800 QPS；② 图遍历用 **BFS**（网页图极深，DFS 会陷入局部）；③ 双层队列——**前队列按优先级**（带偏置随机选择防饿死），**后队列按主机名**（每队列一个工作线程保证串行）；④ 礼貌性：同主机串行 + 请求间隔 + 遵守 `robots.txt` 和 `429 / Retry-After`。
- **追问**：Q「怎么判断页面爬过了？」→ A URL 层用布隆过滤器（无假阴性），内容层用 SimHash / MinHash 检测近似重复。

**第 10 章 · Notification System（通知系统）**
- **一句话定位**：以消息队列为核心、以「至少一次投递 + 消费端幂等」为可靠性基础的扇出型系统。
- **必答**：① 架构：触发服务 → 通知服务器 → 消息队列（按渠道/优先级分区）→ worker → 第三方（APNs / FCM / SMS / Email）；② 可靠性 = 通知日志持久化 + 指数退避重试 + (`event_id`, `user_id`) 去重；③ 幂等必须在**消费端**做；④ 设备令牌生命周期：注册 → 刷新 → 失效（410 / UNREGISTERED）→ 清理；⑤ 偏好按「渠道 × 类别」建模，发送前检查。
- **追问**：Q「怎么保证营销推送不影响验证码？」→ A P0 走独立队列 + 独立 worker 池**物理隔离**，营销走低优先级，系统繁忙时暂停。

**第 11 章 · News Feed System（信息流系统）**
- **一句话定位**：把「多对多聚合」的昂贵操作按用户成本分摊到写侧或读侧，核心决策是**推 / 拉 / 推拉结合**。
- **必答**：① 发布链路与读取链路负载特征不同，分开设计；② **推拉结合**——普通用户推、大 V 拉（粉丝数服从幂律分布）；③ 信息流缓存存 `post_id` 列表 + 长度上限，**不存内容**；④ 扇出异步化（消息队列削峰）；⑤ 五层缓存：信息流 / 内容 / 社交图谱 / 动作 / 计数。
- **追问**：Q「大 V 发帖会怎样？」→ A 纯推模式下 1000 万粉丝 = 1000 万次缓存写入脉冲（约 80 MB，单机约 200 秒），必须走拉模式。

**第 12 章 · Chat System（聊天系统）**
- **一句话定位**：以**有状态长连接**为基础、以「至少一次 + 幂等 + 会话内有序」为可靠性保证的实时系统。
- **必答**：① WebSocket 是首选，SSE 适合单向推送，长轮询是兼容性兜底；② 用**服务发现或 Pub/Sub 把「状态在哪」外部化**，保留水平扩展能力；③ 可靠投递三件套：`client_msg_id` 幂等键 + 服务器 ACK、接收方 ACK + 超时重推、离线箱 + `cur_max_message_id` 拉增量；④ 顺序只需**会话内**（服务器分配 `seq`）；⑤ 群聊主键 `(channel_id, message_id)`。
- **追问**：Q「在线状态成本多大？」→ A 全量广播在 5000 万用户下约 87 万条/秒，不可接受；改成按需拉取 + 短 TTL + 只推给正在看的人 + 防抖。

**第 13 章 · Search Autocomplete（搜索自动补全）**
- **一句话定位**：用 Trie 把「前缀 → Top-K」预计算好，靠内存 + 分片扛高 QPS。
- **必答**：① 两个服务：数据采集（构建 Trie）+ 查询（返回 Top-K）；② **节点缓存 Top-K**，把查询从「遍历子树 + 排序」降到「走前缀 + 读 K 条」；③ 数据裁剪：只留 Top 1 亿热门查询（约 5 GB）；④ 按前缀范围分片（一次前缀查询只命中一个分片）；⑤ 小规模用 KV，大规模用自建 Trie + 序列化 + mmap。
- **追问**：Q「怎么让刚火的词马上出现？」→ A 双层 Trie：基础层天级重建 + 热点层 Kafka + Flink 滑动窗口（Count-Min Sketch）秒级写 Redis，查询时合并。

**第 14 章 · YouTube（视频平台）**
- **一句话定位**：写少读多、**带宽成本主导**的系统——挑战是把同一份内容以最合适的形态、最低成本送到能力各异的终端。
- **必答**：① **控制面与数据面分离**，视频字节走对象存储 + CDN，绝不穿过应用服务器；② 转码是为了**码率阶梯**（不是单纯压缩），异步、长耗时、可重试，用 DAG + 队列组织；③ 上传用**预签名 URL 直传** + 分片并行 + 断点续传；④ 播放走 CDN + **ABR**（分片边界必须 GOP 对齐）；⑤ 成本优化排序：按需转码 > 只把热门放 CDN > AV1 > 自建 CDN。
- **追问**：Q「转码失败怎么处理？」→ A 可恢复的从**预处理器持久化的 GOP 中间态**重试（指数退避 + 抖动），不可恢复的直接终止；重试必须幂等 + 有次数上限 + 死信队列。

**第 15 章 · Google Drive（云盘同步）**
- **一句话定位**：以「多设备最终一致」为核心难题的分布式同步系统——难点在同步协议与冲突判定，不在存储。
- **必答**：① 内容与元数据分离（块按内容哈希寻址，元数据存关系库）；② **块级同步 + 内容定义分块（CDC）**；③ 冲突判定靠**版本向量**（区分顺序更新与并发更新），真冲突**保留双副本**；④ 通知是**提示不是数据**——客户端收到后主动拉元数据 → 再拉缺失的块；⑤ 状态机 + 引用计数。
- **追问**：Q「为什么不用固定大小分块？」→ A 头部插入一个字节会让所有块边界右移，导致 100% 重传；CDC 只重传 1~2 个块（重传量从 100% 降到 5% 以下）。

### 3.4 大型系统（第 16–28 章）

**第 16 章 · Proximity Service（附近服务）**
- **一句话定位**：二维空间范围查询——B+ 树索引解决不了，必须把二维压成一维键（GeoHash）或用空间索引（四叉树 / R 树 / S2）。
- **必答**：① 一维索引无法做二维范围查询；② GeoHash 用 Morton 编码（经纬度位交错）+ base32，共 12 层；③ **必须查相邻格子**（3×3，必要时 5×5），处理反经线环绕；④ 两阶段查询：包围盒粗筛 → Haversine 精筛 → 排序限条数；⑤ 缓存键用 geohash 而非坐标（坐标有 GPS 抖动）。
- **追问**：Q「GeoHash 和四叉树怎么选？」→ A 看**查询类型**（固定半径选 GeoHash，kNN 选四叉树）和**更新频率**（四叉树写代价极高，只适合批量更新）。

**第 17 章 · Nearby Friends（附近好友）**
- **一句话定位**：高吞吐、允许少量丢失的实时位置扇出系统——WebSocket 长连接 + Redis Pub/Sub 广播 + 位置缓存兜底。
- **必答**：① 量级：10M 并发 → 33 万次上报/秒 → **扇出后 1333 万条推送/秒**（上报量与扇出量要分开说）；② 选 WebSocket 因为需要双向；③ Redis 两角色——位置缓存（最新值 + TTL）+ Pub/Sub 频道；④ WebSocket 服务器**有状态**，扩容要处理重连、下线要 draining；⑤ Pub/Sub 是**即发即忘**，靠初始化拉快照 + 版本号检测断档兜底。
- **追问**：Q「一个用户有 5000 个好友怎么办？」→ A 距离阈值过滤（通常只有几十个在范围内）+ 好友数上限兜底 + 必要时降采样；注意**发布侧是集中的**，加服务器解决不了热点频道单点压力。

**第 18 章 · Google Maps（地图）**
- **一句话定位**：三套系统的叠加——位置服务（写密集流）、导航服务（大规模图最短路）、地图渲染（PB 级瓦片分发）。
- **必答**：① Web Mercator（EPSG:3857）等角不等积，算距离必须在 WGS84（EPSG:4326）上做；② 瓦片 Z/X/Y 三级索引，总数 `4^Z`；③ 路网分块 + 分层（路由瓦片带邻接引用）；④ 寻路用 **CH 或 CRP**；⑤ 位置服务：客户端批量上报 → Cassandra → Kafka 分发；⑥ 瓦片分发：预计算 + 矢量瓦片 + CDN + 版本化 URL + 条件请求。
- **追问**：Q「导航怎么在两毫秒内算出 1000 公里路线？」→ A CH 离线收缩节点 + 添加快捷边，查询时双向 Dijkstra 只向高层走；路况频繁变化用 CRP 拆分「拓扑预处理 + 权重定制」。

**第 19 章 · Distributed Message Queue（分布式消息队列）**
- **一句话定位**：可持久化、可复制、可分区的**追加日志**，用「分区内有序 + 多副本 + 消费者组」提供高吞吐、高可用、可重放。
- **必答**：① 分区是扩展和有序的基本单位，**消费者数不能超过分区数**；② 存储用分段日志（WAL），高性能来自顺序写 + 页缓存 + 零拷贝；③ 持久性由 `acks` + `replication.factor` + `min.insync.replicas` **三者共同决定**；④ 消费者用拉模式（速率自控），空转用长轮询；⑤ 投递语义三种：at-most-once / at-least-once / exactly-once（仅在 Kafka 内部成立）。
- **追问**：Q「怎么保证消息不丢？」→ A 三段答：生产者 `acks=all` + 重试 + 幂等；Broker RF≥3 + `min.insync.replicas=2` + 关闭 unclean 选举；消费者**处理完再提交偏移量**。

**第 20 章 · Metrics Monitoring and Alerting（监控告警）**
- **一句话定位**：一条「采集 → 传输 → 存储 → 告警 → 展示」的时序数据管道；技术核心是低成本写入海量时间序列，业务核心是在对的时刻叫对的人。
- **必答**：① 数据模型 =「指标名 + 标签 + 时间戳 + 值」，**标签基数决定内存成本**；② 采集有拉（Prometheus）和推（CloudWatch / Graphite），短任务用 **Pushgateway** 弥补；③ 时序数据库要专门选型，压缩（delta-of-delta + XOR）+ 降采样控成本；④ 传输解耦：采集器写 Kafka，流处理消费后写库；⑤ 告警要配**聚合、抑制、静默**，成熟团队用 SLO + 错误预算驱动。
- **追问**：Q「告警风暴怎么解决？」→ A 三件套——**聚合**（同因合并）、**抑制**（高优先级压制下游衍生告警）、**静默**（维护窗口屏蔽且必须设过期时间）。

**第 21 章 · Ad Click Event Aggregation（广告点击聚合）**
- **一句话定位**：无界数据流上的精确聚合——事件时间对齐窗口、水位线处理乱序、去重与恰好一次保证计费准确、对账兜底。
- **必答**：① 量级：10 亿次/天 → 平均 10k QPS、峰值 50k QPS、每月 3 TB；② 分层：Kafka → Map（按 `ad_id` 重分区）→ Aggregate（内存窗口）→ Reduce，用 DAG 组织；③ 计费必须用**事件时间**，乱序靠水位线 + 允许迟到 + 侧输出流，残余误差靠**日终对账**；④ 去重：系统级幂等写入/两阶段提交，业务级布隆过滤器/Redis SET/Flink State；⑤ 正确性链：恰好一次处理 → 去重 → 对账（叠加，非替代）。
- **追问**：Q「水位线设多长？」→ A 测量「处理时间 − 事件时间」差值的分布，取 **P99**；剩余 1% 交给允许迟到 + 侧输出流，最后靠日终对账兜底。

**第 22 章 · Hotel Reservation System（酒店预订）**
- **一句话定位**：读多写少、量级不大、**并发正确性要求极高**——用数据库原子性裁决有限资源竞争，而非应用层加锁。
- **必答**：① 量级：约 24 万笔/天、**3 TPS**，单库可扛，难点是并发正确性；② 选关系库因为 ACID 保护「库存不能为负」「不能重复扣款」两条底线；③ 把「入住区间」拆成「一行一天」（`room_type_inventory`），总行数 7300 万；④ 并发控制首选**原子条件更新（检查写进 WHERE）+ CHECK 约束兜底**；⑤ 两类重复分开解：同一用户重复提交 → 幂等键 + 唯一约束；多用户并发抢订 → 数据库原子性。
- **追问**：Q「两个用户同时抢最后一间房？」→ A 识别 **TOCTOU 竞态**，把条件写进 `UPDATE ... WHERE total_reserved + 1 <= total_inventory`，然后**检查 `affected_rows`**（1 抢到 / 0 售罄），整个操作放一个事务。

**第 23 章 · Distributed Email Service（邮件系统）**
- **一句话定位**：用户隔离、写多读少、可靠性要求极高、还要对抗恶意输入的分布式系统；难点在元数据建模与送达率运营。
- **必答**：① 协议分工：SMTP 发送/中继，IMAP/POP3 收取；② 按 `user_id` 分片，从根上避开跨分片查询；③ 附件与元数据分离；④ 搜索用**倒排索引 + Kafka 异步增量索引**，绝不用 `LIKE '%x%'`；⑤ 送达率三件套 **SPF + DKIM + DMARC** + IP 预热 + 硬退信自动清理。
- **追问**：Q「邮件为什么被判为垃圾邮件？」→ A 三层看——**身份**（SPF/DKIM/DMARC 是否通过）、**信誉**（IP/域名历史、投诉率、退信率）、**内容与行为**（特征词、互动率、发信量突变）。

**第 24 章 · S3-like Object Storage（对象存储）**
- **一句话定位**：扁平命名空间 + 不可变对象 + 元数据与数据分离，用「牺牲单次延迟」换极高持久性、近乎无限容量、极低成本。
- **必答**：① **不可变 + 扁平命名空间**（`/` 只是字符），不支持随机写，随机读可以（`Range` GET）；② 元数据与数据分离，各自独立扩展；③ 持久性靠故障域隔离 + **纠删码**（8+4 = 1.5x 存储、容忍 4 块；三副本 = 3x、容忍 2 块）；④ **元数据是真正的瓶颈**；⑤ 大文件用分片上传（解决大小上限、断点续传、并行带宽）。
- **追问**：Q「删除一个对象，空间什么时候真正释放？」→ A 删除先写**删除标记**（原子、可恢复），物理空间在**压实（Compaction）**搬走有效对象后才回收，按垃圾占比阈值触发。

**第 25 章 · Real-time Gaming Leaderboard（游戏排行榜）**
- **一句话定位**：实时 Top-K + 个人排名，用 Redis 有序集合把排名查询做到 O(log N)，超出单实例后用分片 + 聚合排名。
- **必答**：① 写接口只对游戏服务器开放，服务端**复算**结果；② Redis 有序集合 = 哈希表 + 跳表，跳表的 **span** 是排名 O(log N) 的关键；③ `ZINCRBY` 加分、`ZREVRANGE` 取前 K、**名次用 `ZCOUNT` 而不是 `ZRANK`**（否则同分名次错）；④ 亿级瓶颈是**内存和单 key**（1 亿成员约 13 GB）；⑤ 分片后全局排名：哈希分片用各分片 `ZCOUNT` 求和（精确但扇出 N 次）。
- **追问**：Q「两个人分数一样，名次一样吗？」→ A `ZRANK` 返回序列位置（同分按成员名字典序），会不同；要并列名次必须用 `1 + ZCOUNT(key, "(score", "+inf")`。

**第 26 章 · Payment System（支付系统）**
- **一句话定位**：核心不是「调第三方接口」，而是用**复式记账保证账目正确**、用**幂等 + 状态机 + 对账**在不可靠网络上实现资金最终一致。
- **必答**：① 复式记账是心脏（借贷两方、金额相等、总和恒为零），账本是事实、钱包是缓存；② 「恰好一次投递」不可能（两将军问题），工程做法是 **at-least-once + 幂等**，三层幂等：客户端幂等键、`payment_order_id`、PSP nonce；③ 状态机必须有 `UNKNOWN`，**模糊态只能查询不能重试**；④ 重试要指数退避 + 抖动 + 上限 + 断路器，终态业务错误绝不重试；⑤ 对账不可省略（T+1 逐笔比对，排除在途交易）；⑥ 不自己存卡号（托管支付页 + token）。
- **追问**：Q「支付请求超时了怎么办？」→ A **不能重试**。先查 `GET /v1/payments/{id}` 确认最终状态：SUCCESS 推进状态机、FAILED 才是真失败、查不到保持 `UNKNOWN` 并退避重查。

**第 27 章 · Digital Wallet（数字钱包）**
- **一句话定位**：用**分布式事务保证转账原子性**，用**事件溯源保证账本可审计可重放**，其余设计（分片、Raft、CQRS、快照）都为在 100 万 TPS 下同时满足这两条。
- **必答**：① 跨库没有本地事务，2PC 的问题是锁竞争 + 协调者单点，改用 **TCC 或 Saga**；② TCC 三阶段（Try 冻结 / Confirm 扣减 / Cancel 解冻）都必须幂等，**Confirm 只能重试不能回滚**；③ **事件溯源**：事件列表是唯一真相，状态和快照都可重建；④ Raft 复制事件列表（组内共识），跨组用 TCC/Saga（组间补偿）；⑤ **CQRS** 分离读写，接受最终一致性。
- **追问**：Q「用户刚转完账立刻查余额，为什么可能是旧值？」→ A 读模型异步从事件流更新，存在**最终一致性窗口**；解法是写后读走权威状态机、推送替代轮询、或等待指定事件序列号。

**第 28 章 · Stock Exchange（股票交易所）**
- **一句话定位**：用**单机单线程的确定性撮合引擎**保证微秒级延迟和主备一致性，用事件溯源保证状态可重放，用组播保证行情分发公平。
- **必答**：① 三条数据流延迟要求不同——交易流微秒级（关键路径）、行情流毫秒级（要求同时性）、报送流不敏感；② 撮合引擎必须**确定性**：单线程 + 输入按序列号严格排序 + 禁用随机数和系统时间；③ 不用普通数据库撮合（`fsync`、锁、GC 造成尾延迟），用内存撮合 + 顺序写 WAL + 异步写库；④ **定序器**给入站订单和出站成交打序列号（及时性/公平性、快速恢复、精确一次）；⑤ 风控必须在撮合**之前**（撮合结果不可逆）。
- **追问**：Q「撮合引擎挂了怎么办？」→ A 主备（Primary-Standby）架构：standby 消费同一份输入日志、执行同样确定性撮合、**不对外发布事件**；leader 挂靠心跳检测，自动切换（状态一直同步所以无缝），跨机器用可靠 UDP 复制事件存储。

## 四、最高频的 30 个追问（跨章节）

> 已按主题去重合并（如「一致性哈希能否解决热 key」在第 1、5、11 章重复出现，合并为一条）。按**难度递增**排序，先扫基础题确认不卡壳，再看高级题。

### 4.1 基础题（必须脱口而出）

**1. 为什么不能用 `hash(key) % N` 做分片？**（第 5、6 章）

<details>
<summary>答案要点</summary>

- N 变化时几乎全部 key 的归属改变，触发全量数据迁移。
- 取模下 key 留在原节点的概率仅约 `1/(N+1)`，迁移量 `N/(N+1)`：3→4 台是 75%，99→100 台是 99%。
- 一致性哈希把迁移比例降到约 `1/N`。
- 更工程化的做法：**预先规划大量逻辑分片**（如 1024 片），扩容时整片搬迁。

</details>

**2. `W + R > N` 为什么能保证强一致？**（第 6 章）

<details>
<summary>答案要点</summary>

- 写入集合大小 W、读取集合大小 R，若 `W + R > N` 则两集合**必有交集**（鸽巢原理）。
- 读取时从 R 个响应中取版本号最高的即可。
- 前提：读取端要能识别版本号。
- N=3、W=R=2 是最常用的均衡配置。

</details>

**3. 为什么需要虚拟节点？设多少个合适？**（第 5 章）

<details>
<summary>答案要点</summary>

- 单点占环时负载相对标准差接近 100%，最忙节点要扛平均值 `ln N + γ` 倍（10 台时 2.9 倍）。
- 用 V 个虚拟节点后相对标准差降到约 `1/√V`：V=64 约 12.5%，V=256 约 6.25%。
- 但 vnode 越多，元数据、修复、启动开销越大，**有收益递减点**。
- 常见取值 64~256；Cassandra 把 `num_tokens` 从 256 降到 16 就是这个权衡。

</details>

**4. 缓存和数据库怎么保持一致？**（第 1 章）

<details>
<summary>答案要点</summary>

- 推荐 **Cache-Aside**：先更新数据库，再**删除**缓存。
- 异步场景可用 CDC 订阅 binlog 做最终一致。
- 强一致场景需要分布式锁，或干脆放弃缓存。
- 缓存是用一致性换性能的交易，必须同时设计失效、穿透、降级策略。

</details>

**5. 为什么不用粘性会话（Sticky Session）？**（第 1、12 章）

<details>
<summary>答案要点</summary>

- 粘性会话让服务器变回**有状态**，导致负载不均、机器故障即掉线、无法自动伸缩。
- 它是临时方案，不是架构方案。
- 正确做法：状态外置（Redis / 服务发现 / Pub-Sub），让服务器保持无状态。
- 聊天场景是正当例外——连接本身就是状态，但要靠服务发现或 Pub/Sub 外部化位置。

</details>

**6. 分页为什么用游标（Cursor）而不是 `offset`？**（第 3、11 章）

<details>
<summary>答案要点</summary>

- 信息流持续变化，`offset` 分页在插入/删除后会导致**重复项和漏项**。
- 游标锚定一个稳定位置（如 `post_id` / 时间戳），不受前后变化影响。
- 游标分页对数据库也更友好（避免大 offset 的深扫描）。
- API 定义时主动给出游标设计是加分项。

</details>

**7. 为什么不能用 UUID 做主键？**（第 7 章）

<details>
<summary>答案要点</summary>

- 128 位超出 `BIGINT` 范围，存储和索引体积翻倍。
- v4 随机无序，在 InnoDB 聚簇索引上导致**频繁页分裂**、写入下降、索引碎片化。
- 非要用就选 **UUID v7**（有序），或降级为二级索引。
- 要 64 位且有序，选 Snowflake / ULID。

</details>

**8. 为什么短链不用 301？**（第 8 章）

<details>
<summary>答案要点</summary>

- 301 被浏览器**永久缓存**，后续请求根本不到服务器。
- 后果：① 无法统计点击；② 无法修改跳转目标；③ **无法撤销恶意链接**。
- 商业短链服务需要这三项能力，所以用 302 / 307。
- 代价是每次跳转都打服务器，靠缓存和分片扛。

</details>

**9. 限流器自己挂了怎么办？**（第 4 章）

<details>
<summary>答案要点</summary>

- 默认 **fail-open**：限流器是保护层，不该成为新的单点。
- 但登录、验证码、支付这类接口要 **fail-closed**，被刷的代价高于短暂不可用。
- 生产实践：**fail-open + 每节点本地内存限流兜底 + 告警**。
- 既不裸奔，也不因 Redis 抖动 5 秒而全站故障 5 分钟。

</details>

**10. 为什么不用两个普通索引做二维范围查询？**（第 16 章）

<details>
<summary>答案要点</summary>

- B+ 树是**严格一维**的：纬度索引能定位纬度范围，但这些记录在经度上完全乱序。
- 两个索引的交集只能靠分别扫描再求交，数据量大时退化成近似全表扫描。
- 复合索引 `(lat, lon)` 也没用——第一个字段是范围查询时第二个字段用不上。
- 必须改用空间索引：GeoHash 压成一维键，或四叉树 / R 树 / S2。

</details>

### 4.2 进阶题（体现深度）

**11. 加了一台机器，缓存为什么大面积失效？怎么算？**（第 5 章）

<details>
<summary>答案要点</summary>

- 取模哈希下 key 留在原节点需 `hash % N == hash % (N+1)`，概率仅约 `1/(N+1)`。
- 所以约 `N/(N+1)` 的 key 要迁移：3→4 台 75%，99→100 台 99%。
- 一致性哈希降到约 `1/N`（3→4 台 25%）。
- 注意 `1/N` 是**哈希空间**比例，实际迁移**数据量**取决于那段区间里真实存了多少。

</details>

**12. 大 V 发帖会怎样？怎么判断该推还是该拉？**（第 11 章）

<details>
<summary>答案要点</summary>

- 纯推模式下 1000 万粉丝 = 1000 万次缓存写入脉冲（约 80 MB，单机约 200 秒），会打垮集群。
- 解法：大 V 走拉模式，只写自己的发件箱；粉丝读取时现拉（通常只关注几十个大 V）。
- 判定：按**粉丝数阈值**（经验值如 1 万）动态判定，阈值随集群负载调整。
- 叠加活跃度：**不活跃用户一律不推**（能砍掉大部分扇出量），登录时按拉模式重建。

</details>

**13. 消息怎么保证不丢？**（第 12、19 章）

<details>
<summary>答案要点</summary>

- **生产者侧**：`acks=all` + 重试 + 幂等生产者。
- **Broker 侧**：RF≥3 + `min.insync.replicas=2` + `unclean.leader.election.enable=false`。
- **消费者侧**：处理完再提交偏移量。
- 聊天场景：`client_msg_id` 幂等键 + 服务器 ACK、接收方 ACK + 超时重推、离线箱 + `cur_max_message_id` 拉增量。
- 任何一段缺失都可能丢消息。

</details>

**14. 怎么保证不重复（扣款 / 消费）？**（第 19、26 章）

<details>
<summary>答案要点</summary>

- 队列侧**做不到端到端去重**：要么接受重复 + 消费端幂等（推荐），要么在 Kafka 内部用事务 + 幂等生产者。
- 业务侧最实用的是**唯一索引 + UPSERT**。
- 支付三层幂等：客户端幂等键（挡住重复提交）、`payment_order_id`（挡住重复创建）、PSP nonce（挡住重复扣款）。
- 幂等键过期时间必须 ≤ PSP 的幂等窗口（常见 24 小时），过期后保证失效。

</details>

**15. 服务器时钟被 NTP 往回拨了 1 秒，Snowflake 会怎样？**（第 7 章）

<details>
<summary>答案要点</summary>

- 会生成与 1 秒前**相同的 ID**（时间戳和序列号都相同），破坏唯一性。
- 这是**正确性问题**，不是性能问题。
- 处理：短回拨（< 5 ms）自旋等待；超过阈值抛异常 + 告警；更优雅的是预留位记录回拨次数。
- 用 `slew` 模式 + 内部保护双保险，或改用 ULID / UUID v7（80 位随机数让回拨不再致命）。

</details>

**16. 一致性哈希能解决热点 key 吗？**（第 1、5、11 章）

<details>
<summary>答案要点</summary>

- **不能**。同一个 key 永远映射到同一个节点，无论怎么哈希。
- 它解决的是**分区倾斜**（分布是否均匀），不是热 key。
- 热 key 要靠：缓存、key 加盐（`hot_key_0`~`hot_key_9` 分散到多节点）、独立分片。
- 第 21 章的热点广告同理——两阶段聚合或加盐拆分。

</details>

**17. 为什么云盘不用固定大小分块？**（第 15 章）

<details>
<summary>答案要点</summary>

- 固定分块下，**文件开头插入少量数据会让所有块边界右移**，每个块的哈希都变，导致 100% 重传。
- **内容定义分块（CDC）**用滚动哈希让边界由内容决定，插入点之后很快重新对齐，只重传 1~2 个块。
- 编辑模式以「开头插入」为主时，两者差距可达 20 倍以上。
- 代价：块大小不固定，索引和参数调优更复杂。

</details>

**18. 两台设备同时改了同一个文件，怎么处理？**（第 15 章）

<details>
<summary>答案要点</summary>

- 先判因果：用**版本向量**比较两个版本——一方支配另一方则是顺序更新，直接采用新的；互不支配则是真并发冲突。
- 冲突时服务端版本保留原文件名，客户端版本另存为**带冲突标记的新文件**并通知用户，保证零数据丢失。
- **绝不用时间戳做 LWW**：设备时钟不可信，且无法区分并发与顺序。
- 这条约束（数据丢失不可接受）同时排除了 LWW 和异步复制的故障转移。

</details>

**19. GeoHash 有什么坑？和四叉树怎么选？**（第 16 章）

<details>
<summary>答案要点</summary>

- 核心是**单向保证**：「前缀相同 ⇒ 距离近」成立，「距离近 ⇒ 前缀相同」不成立。
- 相邻格子只共享父级前缀；赤道两侧相距 22 米的点可能因纬度位翻转而零共享前缀。
- 解法：查询 3×3（半径大时 5×5）邻域，处理反经线环绕与两极退化。
- 选型看两件事——**查询类型**（固定半径选 GeoHash，kNN 选四叉树）和**更新频率**（四叉树写代价极高，只适合批量更新）。

</details>

**20. 为什么对象存储用纠删码而不是三副本？**（第 24 章）

<details>
<summary>答案要点</summary>

- 对象存储面向**延迟不敏感的温冷数据**，成本是第一约束。
- 8+4 纠删码：1.5x 存储开销、容忍 4 块丢失；三副本：3x、容忍 2 块。
- 纠删码在成本和容错上都更优，代价是**读取延迟更高、实现更复杂**。
- 延迟敏感场景（数据库、缓存）仍用副本；同一系统内常常两者并存（元数据用副本，数据用纠删码）。

</details>

**21. 分片之后怎么算全局排名？同分名次怎么算？**（第 25 章）

<details>
<summary>答案要点</summary>

- 哈希分片：用 `ZCOUNT` 扇出求和，**结果精确**，代价是 N 次网络往返、尾延迟受最慢分片影响。
- 分数范围分片：更高分片的 `ZCARD` 之和 + 本分片 `ZCOUNT`。
- 同分名次：`ZRANK` 返回序列位置（同分按成员名字典序），会拿到不同值；并列名次必须用 `1 + ZCOUNT(key, "(score", "+inf")`。
- 规模再大就退化成百分位近似。

</details>

**22. 水位线设多长？**（第 21 章）

<details>
<summary>答案要点</summary>

- 先测量「处理时间 − 事件时间」差值的分布，取 **P99** 作为水位线长度。
- 剩余 1% 交给**允许迟到 + 侧输出流**处理。
- 最后靠**日终对账**兜底。
- 关键：水位线是**估计不是保证**，零丢失只能靠对账，不能靠调参数。

</details>

### 4.3 高级题（区分度所在）

**23. 支付请求超时了怎么办？**（第 26 章）

<details>
<summary>答案要点</summary>

- **不能重试**。超时是**模糊态**，钱可能已经扣了，重试就是重复扣款。
- 必须先调用查询接口确认最终状态：SUCCESS 推进状态机、FAILED 才是真失败、查不到就保持 `UNKNOWN` 并退避重查。
- 判断依据：如果失败原因是「我不知道发生了什么」，就不能重试。
- 前端只展示「处理中」而不是「失败」。

</details>

**24. 为什么要复式记账？直接改余额不行吗？**（第 26 章）

<details>
<summary>答案要点</summary>

- 直接改余额有七个问题：没有审计轨迹、没有可校验的不变量、错误无法被发现、无法归因、无法对账、并发下需要加锁、历史被覆盖。
- 复式记账提供**借贷平衡**这个可随时校验的不变量——任何错误都会让账不平，从而暴露。
- 分录只追加，修正用**红冲**，不修改历史。
- 每个资金停留过的地方都要账户，尤其是 **PSP 清算账户**（应收款）。

</details>

**25. 为什么不用 2PC 而用 TCC？Confirm 一直失败怎么办？**（第 27 章）

<details>
<summary>答案要点</summary>

- 2PC 在 Prepare 到 Commit 之间**锁住资源**，高并发下锁竞争是致命瓶颈，且协调者是单点。
- TCC 把每个阶段拆成独立的本地事务，**不长期持锁**，可并行执行，延迟更低；代价是复杂度从数据库层转移到业务层。
- Confirm **不能回滚，只能幂等重试直到成功**——待重试事务落库，后台任务持续重试 + 告警。
- 这也是为什么 Confirm 的逻辑必须尽可能简单、可靠；三种失败模式（Confirm 必重试、空回滚、悬挂）统一用阶段状态表 + 事务 ID 解决。

</details>

**26. 为什么事件列表必须持久化，命令列表却不用？**（第 27 章）

<details>
<summary>答案要点</summary>

- **命令是非确定性的**：可能失败、可能依赖外部 IO，无法从命令重放出确定的事件。
- **事件是已确定的事实**：重放结果永远一致。
- 所以事件列表是真相来源（source of truth），状态和快照都只是可重建的物化视图。
- 因此只需要保证事件列表的高可靠（Raft 复制 + 顺序一致），配合 CQRS 维护读模型。

</details>

**27. 为什么撮合引擎要单线程？它挂了怎么办？**（第 28 章）

<details>
<summary>答案要点</summary>

- 多线程执行顺序由 OS 调度决定，**不可复现**，会破坏确定性，导致主备状态分叉。
- 单线程**没有锁竞争**，延迟更可预测；现代 CPU 单核每秒处理数百万笔订单是现实可达的。
- 挂了的处理：**主备（Primary-Standby）**——standby 消费同一份输入日志、执行同样确定性撮合、**不对外发布事件**；靠心跳检测自动切换，因为状态一直同步所以无缝。
- 跨机器时用**可靠 UDP** 复制事件存储。

</details>

**28. 为什么行情用 UDP 组播，订单不用？**（第 28 章）

<details>
<summary>答案要点</summary>

- 行情是**完整状态快照流**，丢一帧可由下一帧覆盖或主动拉快照恢复。
- 订单是**增量事件**，丢一笔就是永久的资金差错。
- 所以行情追求**同时性和低延迟**（组播 + UDP），订单追求**不丢不重**（序列号 + 确认 + 重传）。
- 组播让源只发一份、由路由器在网络分叉点复制，所有订阅者从分叉点起**同时出发**；单播发 N 份会让先收到的人获得信息优势。

</details>

**29. Flink 怎么做端到端恰好一次？**（第 21 章）

<details>
<summary>答案要点</summary>

- 三段式：① **检查点**（Chandy-Lamport 快照）保证状态不丢不重；② **两阶段提交 Sink**（预提交 → 检查点完成 → 提交）保证输出不重；③ 如果 Sink 天然幂等（UPSERT），可以省掉②。
- 先问下游是否幂等，再决定要不要上事务——**幂等是最便宜的解法**。
- 注意边界：Kafka / Flink 的 exactly-once 只是「状态更新 + offset 提交的原子性」，管不了外部副作用。

</details>

**30. 1000 万用户在线，长连接 / 通知服务怎么扛？**（第 15 章）

<details>
<summary>答案要点</summary>

- 按 `user_id` **一致性哈希分片**，保证同一用户的所有设备连到同一台推送服务器。
- 用 **epoll** 支撑单机十万级连接，把 `ulimit -n` 调高。
- 客户端重连加**随机抖动 + 指数退避**，防重连风暴（惊群）。
- 移动端用 APNs / FCM **唤醒后走 API 拉取**，不依赖推送通道传数据（推送是 best-effort）。

</details>

## 五、容易答错的地方

> 「错误说法 → 正确说法」对照表，从各章「常见误区」提炼去重。面试中一旦说出左列，会直接暴露认知漏洞。

| 错误说法 | 正确说法 |
|---|---|
| 加机器就能解决扩展问题 | 瓶颈永远在**有状态的数据层**；Web 层易扩，数据层难扩，且多机引入负载均衡、分片、状态同步 |
| NoSQL 比 SQL 更先进 | NoSQL 是用事务和 JOIN 换水平扩展；**默认选 SQL**，除非有明确理由 |
| SLA 99.9% 说明每月只停 43 分钟 | SLA 是**赔付承诺的下限**，不是实际水平；它是商务条款不是技术指标 |
| 存 55 PB 数据就买 55 PB 硬盘 | 要乘副本数（×3）甚至更多，还要留 20% 余量 |
| 布隆过滤器能准确判断元素存在 | 有**假阳性**：说「不在」一定准，说「在」可能不准 |
| 布隆过滤器能解决哈希碰撞 | 只能做**前置过滤**，真正裁决者是数据库唯一索引 |
| 数据量不大就不会有碰撞 | 生日悖论：约 `√M` 次插入就有 50% 碰撞概率 |
| 爬虫越快越好 | 速度不是权利，**礼貌性是第一原则**；不礼貌会被封甚至违法 |
| 哈希比对就能检测重复内容 | 只能检测字节级一致；互联网上大多是近似重复，需 SimHash / MinHash |
| 调用第三方 API 成功 = 用户收到了 | APNs / FCM / 短信全是 best-effort，重要通知需**应用内消息箱兜底** |
| 用 event ID 去重就够了 | 一个事件扇出多个用户，幂等键必须是 (`event_id`, `user_id`) |
| 信息流就是「把好友帖子按时间排一下」 | 大规模用**推拉结合**：普通用户推、大 V 拉 |
| 聊天用 WebSocket 就万事大吉 | 通道之上还需 **ACK + 幂等键 + 会话内序号 + 离线箱** |
| 转码就是为了压缩体积 | 核心目的是构建**码率阶梯**以支持自适应播放（ABR） |
| MP4 是一种视频编码 | MP4 是**容器**；能否播放取决于**编码** |
| 云盘的难点在存储 | 对象存储早解决了存储；真正的难点是**多设备一致性与冲突判定** |
| 通知服务可以把变更内容直接推给客户端 | 通知会丢失/重复/乱序；它只做**提示**，客户端主动拉权威数据 |
| Redis Pub/Sub 就是消息队列 | 不持久化、无 Ack、无重放、无消费者组；需要可靠投递用 Streams / Kafka |
| 降低上报频率就能解决扇出问题 | 扇出量 = 频率 × 好友数 × 在线率，**大头是好友数** |
| 地图上的距离可以直接用平面坐标算 | Web Mercator 等角不等积（尺度因子 `1/cos²φ`），算距离要用 WGS84 + haversine |
| 瓦片数量随缩放级别线性增长 | 每级一分为四，总数是 `4^Z`（指数增长） |
| Kafka 快是因为「消息存在内存里」 | 消息**持久化到磁盘**；快在顺序追加写 + 稀疏索引 + 零拷贝 + 页缓存 |
| 消息队列保证全局有序 | 只保证**分区内**有序，跨分区无序 |
| 监控指标越多越好 | 每条时间序列都占内存和磁盘，指标要服务于具体告警与排查场景 |
| 标签随便加，方便排查 | 标签取值是**相乘**的，一个高基数标签能让序列数涨百万倍 |
| 用平均值看延迟就够了 | 平均值会掩盖慢请求，要看**分位数**（P95 / P99 / P999） |
| 用处理时间就够了，事件时间太复杂 | 计费、归因类场景必须用**事件时间**；处理时间会随网络抖动漂移 |
| `UPDATE` 没报错就说明扣减成功了 | 影响 0 行时**不报错**，必须检查 `affected_rows` |
| 乐观锁一定比悲观锁快 | 高并发下乐观锁失败率接近 100%，低争用才用乐观锁 |
| 库存和订单应该拆成两个微服务 | 「扣库存 + 写订单」必须原子，应放同一个数据库事务；有明确扩展需求再拆 |
| SMTP 负责收发邮件 | SMTP 只负责**发送和中继**，收信用 IMAP / POP3 / HTTPS |
| POP3 和 IMAP 只是「删不删邮件」的区别 | 真正的区别是**状态存在客户端还是服务端** |
| 配了 SPF 和 DKIM 就不会被伪造 | 二者都不校验用户看到的 `From:` 头，必须加 **DMARC** 对齐检查 |
| 用 `LIKE '%关键词%'` 就能做邮件搜索 | 前导通配符让索引失效，退化为全表扫描，必须用**倒排索引** |
| 对象存储里也有「文件夹」 | 命名空间是扁平的，`/` 只是普通字符；「文件夹」是客户端聚合出的视图 |
| 99.999999999% 说的是可用性 | 这是**持久性**（数据不丢的概率），不是可用性 |
| 对象存储是最终一致的 | 2020-12-01 起，S3 的 GET/PUT/LIST 及元数据变更**全部强一致** |
| 纠删码更先进，所以应该都用纠删码 | 纠删码读取延迟更高；**延迟敏感用副本，延迟不敏感用纠删码** |
| 分片上传生成的 ETag 就是文件的 MD5 | 它是「各分片 MD5 拼接后再取 MD5」并带 `-N` 后缀，不能用于校验或去重 |
| 删除对象后空间立刻就释放了 | 删除只写**删除标记**，空间要等**压实（Compaction）**后才回收 |
| 排行榜就是 `ORDER BY score` | 关系库能答「前 10 名」，答不了「我排第几」的**排名查询** |
| 同分的人 `ZRANK` 会返回相同的值 | `ZRANK` 返回序列位置（同分按字典序），要并列名次必须用 `ZCOUNT` |
| 起了 Redis 副本就不会丢数据 | 主从默认异步，主节点复制完成前宕机仍会丢；排行榜是派生数据，**从源重建才是正解** |
| 幂等做得好就不会有不一致 | 你和 PSP 是两个独立失败域；**对账无法被工程手段取代**，是最后一道防线 |
| 追求 exactly-once delivery | 两将军问题证明不可能；追求 **at-least-once + 幂等 = 恰好一次效果** |
| 指数退避就够了 | 没有抖动会形成惊群；要指数退避 **+ 抖动** + 最大次数 + 断路器 |
| 平均延迟低就够了 | 交易对时间极敏感，要优化**尾延迟**（p99 / p99.9），不看平均值 |

**C. 关键架构图（能徒手画出）**

- [ ] **限流器**：客户端 → API 网关（Lua + Redis）→ 服务，含 fail-open 兜底。
- [ ] **一致性哈希环**：环 + 虚拟节点 + 顺时针归属 + 添加/移除节点时的区间转移。
- [ ] **短链服务**：写（ID 生成器 → Base 62 → 唯一索引）／读（缓存 → 分片库）。
- [ ] **信息流**：发布链路（扇出服务 + 消息队列）／读取链路（时间线缓存 + 内容缓存），标注推拉分界。
- [ ] **聊天**：WebSocket 接入 + 服务发现 / Pub-Sub 路由 + 离线箱 + 会话内 `seq`。
- [ ] **消息队列**：分区 + 多副本（ISR）+ 消费者组 + 分段日志。
- [ ] **支付**：幂等键 → 状态机（含 `UNKNOWN`）→ 复式记账 → TCC → 对账。
- [ ] **交易所**：网关 → 定序器 → 单线程撮合（主备）→ 行情组播；标注「风控在撮合前」。

**D. 高频陷阱自查（能一句话答出）**

- [ ] 「模糊态只能查询不能重试」——超时、`UNKNOWN`、支付。
- [ ] 「前端校验只是体验优化，正确性靠数据库」——幂等键 + 唯一约束 + 条件更新。
- [ ] 「通知只做提示，数据靠拉取」——推送不可靠，拉取幂等。
- [ ] 「推还是拉，看粉丝数分布」——幂律分布决定推拉结合。
- [ ] 「水位线是估计，对账是保证」——零丢失靠对账。
- [ ] 「持久性 ≠ 可用性」——对象存储的 11 个 9 说的是持久性。
- [ ] 「单机单线程换确定性」——撮合引擎。
- [ ] 「exactly-once 是组合效果，不是单一保证」——检查点 + 事务性 Sink / 幂等。
