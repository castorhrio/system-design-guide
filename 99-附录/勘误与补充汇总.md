# 勘误与补充汇总

> 本文件汇总了全部 28 章对原英文笔记的**勘误**与**补充**。
>
> 原项目 `liquidslr/system-design-notes` 是一份很好的速查笔记，但它压缩了大量工程细节，
> 也存在术语过时、技术表述不准确、数字陈旧和内容缺失的问题。
> 这份汇总把这些问题集中列出，方便你对照检查自己的认知。
>
> 每条格式为：**问题** → **正确说法**。完整论述请回到对应章节的「勘误与补充」小节。
>
> **阅读建议**：先看第一节「按错误类型速查」，这里回答的是「我学的哪些东西是错的」；
> 再按需查第二节的逐章明细。

### 1.2　技术事实错误

| 问题 | 正确说法 | 章节 |
|---|---|---|
| 消息队列「持久化组件，存在内存中」 | 持久化到磁盘；高性能来自顺序写、页缓存、零拷贝 | 第 1 章 |
| 主库故障转移靠「数据恢复脚本」 | 半同步复制 + GTID/LSN 位点切换 + Patroni/Orchestrator 自动故障转移 | 第 1 章 |
| 一致性哈希能解决分片倾斜与名人问题 | 只降低节点增减时的迁移比例（约 1/N），不解决热点 key | 第 1、5、11 章 |
| 基本一致性哈希「保证均匀分布」 | 只保证迁移代价小；均匀分布要靠虚拟节点逼近 | 第 5 章 |
| Mitigates Hotspots（缓解热点） | 只缓解分区倾斜，不缓解热点 key | 第 5 章 |
| CAP 是「三选二」 | P 是必选项，现实只有 CP / AP，CA 系统不存在 | 第 6 章 |
| W = 1 就会读到旧数据 | W + R > N 仍强一致；W=1 的真实风险是持久性 | 第 6 章 |
| NTP 能解决时钟问题 | NTP 只能减小漂移，step 模式本身会造成回拨 | 第 7 章 |
| 布隆过滤器能「解决」哈希冲突 | 只能做前置过滤；冲突裁决必须由数据库唯一索引承担 | 第 8 章 |
| 唯一性表述为「每个长 URL 映射到一个短码」 | 真正约束是「短码 → 长 URL 一对一」（方向相反） | 第 8 章 |
| 301 只是「省资源、少统计」 | 301 无法改跳转目标、无法撤销恶意链接、点击数据严重失真 | 第 8 章 |
| 哈希比对检测重复内容 | 只能查字节级精确重复；近似重复需 SimHash / MinHash | 第 9 章 |
| URL Frontier 是一个 FIFO 队列 | 是双层队列系统：前队列按优先级、后队列按主机名 | 第 9 章 |
| Crawl-delay 是 robots.txt 标准指令 | 非官方标准，Google 不支持；应关注 429 / Retry-After | 第 9 章 |
| 用单个 event ID 去重 | 幂等键必须是 (event_id, user_id) 组合 | 第 10 章 |
| 「Distributed Crawling」是通知系统优化项 | 与通知无关，系跨章节误抄，应删除 | 第 10 章 |
| 调用第三方成功即送达 | 推送是 best-effort，需应用内消息箱兜底 | 第 10 章 |
| 「按时间倒序」是现代信息流主流做法 | 现代主流用算法排序；时间倒序是教学简化 | 第 11 章 |
| E2EE 列在「未来扩展」 | 是架构级决策，须在架构阶段决定并设计替代方案 | 第 12 章 |
| WebSocket 就能保证消息可靠 | 通道不保证不丢、不重、不乱序 | 第 12 章 |
| Presence 用全量广播可行 | 规模下成本不可接受，需按需拉取 + 短 TTL 缓存 | 第 12 章 |
| 补全查询「遍历子树」与「节点缓存」并列 | 自相矛盾；主路径是走前缀 + 直接读节点缓存的 Top-K | 第 13 章 |
| KV 存储与 Trie 是等价选项 | 性能特征完全不同：KV 失去前缀共享且每次查询一次网络往返 | 第 13 章 |
| 「实时处理不现实」（补全系统） | 双层 Trie / Lambda 架构可做到秒到分钟级 | 第 13 章 |
| 每日存储 150 TB 未给前提 | 需补「只有约 10% 的 DAU 会上传」这一前提 | 第 14 章 |
| 转码主要是为了省空间 | 核心目的是构建码率阶梯以支持 ABR | 第 14 章 |
| 主库故障直接「提升副本」 | 异步复制下会永久丢写入，违反 RPO=0；须半同步复制 + GTID/LSN 位点切换 + 自动故障转移 | 第 15 章 |
| `latitude BETWEEN :lat - radius` 用「度」减「米」 | 单位不匹配，查询覆盖整个地球；须除以 111320，经度还要乘 `cos(纬度)` | 第 16 章 |
| GeoHash「20 km → 长度 4」 | 长度 4 格子纬度方向仅约 19.6 km，小于半径；改用长度 3 或把邻域扩到 5×5 | 第 16 章 |
| 「GeoHash 前缀越长越近」被当作双向性质 | 只有单向成立；「距离近 ⇒ 前缀相同」错（赤道两侧相距 22 米可能零共享前缀） | 第 16 章 |
| 「每秒 1400 万次位置更新」 | 那是扇出推送量（约 1333 万/秒）；位置上报量是 33.4 万/秒，两者差一个数量级 | 第 17 章 |
| 「为所有用户预分配 Pub/Sub 频道」 | Redis 频道隐式存在、无预分配操作；真正要缓存的是「频道 → 节点」的哈希环映射 | 第 17 章 |
| 地图瓦片「based on their geohash」 | 瓦片用 Z/X/Y 整数三元组；geohash 用于「一组点」的邻近查询 | 第 18 章 |
| Web Mercator「modified」未解释 | EPSG:3857 是投影坐标系、单位为「伪米」，面积尺度因子 `1/cos²φ`；算距离须在 EPSG:4326 上用 haversine | 第 18 章 |
| 「地理编码数据库用 Redis 存 KV」 | 只覆盖反向地理编码；正向（地址→坐标）需倒排索引或 Nominatim / Pelias | 第 18 章 |
| 路线规划「Dijkstra 或 A* 的变体」 | 现代做法是 Contraction Hierarchies（CH）或 CRP，加速 500~1000 倍 | 第 18 章 |
| 「分区 Leader 创建副本分配方案」 | 副本分配与 Leader 选举由 **Controller** 负责 | 第 19 章 |
| 「用 `acks` 一个参数保证持久性」 | 持久性 = `acks` + `replication.factor` + `min.insync.replicas` 三者共同决定 | 第 19 章 |
| 行协议示例 `CPU.load host=... 1613707265 50` | 字段须写成 `名=值` 且位于时间戳之前；且 Prometheus 并不使用行协议 | 第 20 章 |
| 「Pull 用 TCP、Push 用 UDP」 | 只有 StatsD 默认 UDP；Graphite/CloudWatch/OTLP/Prometheus remote write 都跑在 TCP 上 | 第 20 章 |
| 「每个指标名一个 Kafka 分区」 | 千万级序列 = 千万级分区，不可行；应按指标名哈希分区 | 第 20 章 |
| CHECK 约束 `total_reserved <= total_inventory` | 与「允许超卖 10%」需求冲突；应为 `total_reserved <= total_inventory * 1.1`，且比例应参数化 | 第 22 章 |
| 扣减库存 `UPDATE` 漏掉 `hotel_id` 过滤 | `room_type_id` 非全局唯一，会误扣所有酒店的库存；必须补 `WHERE hotel_id = ?` | 第 22 章 |
| `room_type_rate` 表没有 `room_type_id` 列 | 名为「房型价格」却无法表达「不同房型不同价格」；主键应为 `(hotel_id, room_type_id, date)` | 第 22 章 |
| 「`status` 代表某个房间的状态机」 | 它是**预订（reservation）**的状态机（Pending→Paid/Canceled/Rejected、Paid→Refunded） | 第 22 章 |
| 分片策略两条要点都写成 `bucket_id` | 第二条应为按 `object_id` 分片（负载均匀但查询变慢），是明显笔误 | 第 24 章 |
| 「三副本 = 6 个 9」 | 该算法忽略副本修复（MTTR）；纠删码的真正优势是省存储（1.5x vs 3x），不是把持久性从 6 个 9 变 11 个 9 | 第 24 章 |
| 「对象存储强一致」无上下文 | S3 自 **2020-12-01** 起 GET/PUT/LIST 及标签、ACL、元数据变更全部强一致，EMRFS Consistent View / S3Guard 不再需要 | 第 24 章 |
| 用 `INFO keyspace` 取 sorted set 成员数 | 它只返回 key 数量；正确命令是 `ZCARD key`（O(1)） | 第 25 章 |
| 「Redis Cluster 是代理，类似一致性哈希」 | 它无代理、去中心化；用 **16384 个固定哈希槽** + `MOVED`/`ASK` 重定向，不是一致性哈希 | 第 25 章 |
| 「哈希分片下无法确定用户排名」 | 用 `ZCOUNT` 扇出可精确求和，结果精确，代价是扇出随分片数线性增长 | 第 25 章 |
| 「用 `ZREVRANK` 拿名次」（与「同分名次相同」需求矛盾） | `ZRANK` 返回序列位置，同分按成员名字典序不同；须用 `1 + ZCOUNT(key, "(score", "+inf")` | 第 25 章 |
| `accountID.hashCode() % partitionNumber` | Java 负数取模返回负值，会下标越界；应用 `Math.floorMod`，并考虑改一致性哈希/逻辑分片 | 第 27 章 |
| 撮合伪代码 `min(limitIter.next.quantity, order.quantity)` | 应为 `leavesQuantity`（剩余待成交量），否则部分成交时累计超卖 | 第 28 章 |
| 订单状态只有 `new / canceled / filled` | 缺少 `PARTIALLY_FILLED`；至少需要 NEW / PARTIALLY_FILLED / FILLED / CANCELED / REJECTED | 第 28 章 |
| 事件溯源链接 `../chapter28` | 数字钱包是第 27 章，应为 `../chapter27`，否则自我引用 | 第 28 章 |

### 1.3　数字与数据过时

| 问题 | 正确说法 | 章节 |
|---|---|---|
| 延迟数字表标注 2020 年，实为 2010 年前后数据 | SSD 随机读 150 µs → 20~100 µs（NVMe）；内存与 SSD 差距从约 1500 倍缩到约 500 倍 | 第 2 章 |
| text: 140 bytes | 推文上限 2017 年已提高到 280 字符；且字符数不等于字节数 | 第 2 章 |
| 只算写 QPS = 3500 | 必须算读 QPS：约 8.7 万，读写比约 25 : 1 | 第 2 章 |
| 限制前缀长度到 50 | 实际分界点在 20–30 字符，目的是给 Trie 深度设上界 | 第 13 章 |
| YouTube 日观看 50 亿次（2020） | Shorts 单日观看量已超 2000 亿次 | 第 14 章 |
| 每分钟上传 500 小时 | 官方已改用「平均每天上传超过 2000 万个视频」 | 第 14 章 |
| 广告收入 151 亿美元（2019） | 应更新为 2024 年 361 亿美元（Alphabet 10-K） | 第 14 章 |
| 「37% 移动流量来自 YouTube」 | 未注明来源与年份，不宜作为事实引用 | 第 14 章 |
| 碰撞概率被隐性低估 | 生日悖论：7 位十六进制字符约 1.6 万条即 50% 碰撞 | 第 8 章 |
| 单个视频上限 1 GB 被当作真实限制 | 是简化假设；真实上限为「12 小时或 256 GB 取较小者」 | 第 14 章 |
| 「总存储 500 PB」无推导 | `1000万 × 10GB = 100 PB`；须补约 2 倍版本历史 × 2.5 倍冗余；更值得记的是配额（100 PB）与真实占用（约 3.65 PB/年）差近 30 倍 | 第 15 章 |
| `Search QPS = 5000` | 按原数字应为约 5800；还须乘 2~3 倍峰值系数 → 峰值约 1.2 万~1.7 万 QPS | 第 16 章 |
| 「每天 2500 万次实时位置更新」 | 与本章自身估算差约 800 倍（逐秒算差 4 个数量级）；更可能指「每天 2500 万次地图数据更新」，但口径原文未说明 | 第 18 章 |
| 「~70 PB」无推导口径 | 理论瓦片总量约 5.86 万亿块、约 29,000 PB；70 PB 是去重 + 矢量瓦片 + 按需生成后的**实际存储量** | 第 18 章 |
| 格陵兰岛看起来比非洲大 | 格陵兰约 216.6 万 km²，非洲约 3037 万 km²（约 14 倍）；格陵兰中心纬度约 72°N，面积被放大约 10.5 倍 | 第 18 章 |
| 「HDDs can achieve several MB/s」 | 现代 7200 RPM HDD 顺序读写 150~250 MB/s；随机访问才只有 100~200 IOPS | 第 19 章 |
| 降采样 10s→30s 得 `19, 25` | 每桶正好 3 个点，正确值是 **15.3 和 26.7** | 第 20 章 |
| InfluxDB「8 核 32G 下 25 万次写入/秒」 | 这是厂商基准测试的理想值，不能当生产预期；须用自己的数据压测 | 第 20 章 |
| 「三副本 = 6 个 9」/ AFR 0.81% | AFR 因型号年份差异很大，任何具体数字只能当量级参考 | 第 24 章 |
| 「5mil DAU and 25mil MAU」vs「With 50mil DAU」 | 反推应为 **500 万 DAU**（500 万 ÷ 10 万秒 = 50 人/秒） | 第 25 章 |
| 「peak online users = 250 users per second」 | `DAU ÷ 秒数` 是到达率，不是同时在线；并发数 = 到达率 × 停留时长（约 `50 × 600 = 3 万`） | 第 25 章 |
| 「ID 24 字符 + score 16 位 = 26 字节」 | Redis 分数是 8 字节双精度，且忽略内部开销（实际约 120~150 字节/成员）：2500 万约 3~3.5 GB，5 亿约 65 GB | 第 25 章 |
| 「100 万 TPS」被当作常态 | 真实大型支付系统峰值在每秒几十万笔量级；100 万 TPS 是面试刻意放大的设计目标 | 第 27 章 |

### 1.4　概念混淆

| 问题 | 正确说法 | 章节 |
|---|---|---|
| LRU 是「最流行」淘汰策略（暗示唯一） | 需了解 LFU、W-TinyLFU，按访问模式选型 | 第 1 章 |
| Lua 脚本与有序集合并列为两种方案 | Lua 是保证原子性的手段，Sorted Set 是数据结构，二者协作 | 第 4 章 |
| 限流 / 节流 / 熔断 / 降级混用 | 四个不同概念，混用是面试减分项 | 第 4 章 |
| CAP 中的 C = 日常说的「数据一致」 | 特指线性一致性（Linearizability） | 第 6 章 |
| 虚拟节点只是为了让分布更均匀 | 还能表达机器能力差异，实现异构支持 | 第 6 章 |
| 「Queue Selector」被用于两个不同阶段 | 应区分队列选择器（前队列）与队列路由器（前后队列转换） | 第 9 章 |
| AppKey/AppSecret 与 APNs/FCM 鉴权混为一谈 | 是两层鉴权：对外用 AppKey/AppSecret，对下用证书/令牌/服务账号 | 第 10 章 |
| 一致性哈希被描述为「均匀分发请求」 | 用于数据分片；请求分发是负载均衡器的职责 | 第 11 章 |
| E2EE 能保护一切隐私 | 只保护内容，元数据（谁与谁、何时、多频繁）服务器仍可见 | 第 12 章 |
| MP4 是一种视频编码 | MP4 是容器；能否播放取决于编码 | 第 14 章 |
| HLS / DASH 是编码格式 | 是打包 + 传输协议，与编码正交 | 第 14 章 |
| 预签名 URL 是一种加密 | 本质是带签名和有效期的限时授权 | 第 14 章 |
| 「First processed version wins」 | 「wins」误导为丢弃另一版本；正确表述是服务端保留原名、客户端版本另存为冲突副本（保留双副本），冲突判定靠版本向量而非时间戳 | 第 15 章 |
| Redis Pub/Sub 未说明投递语义 | 它是**至多一次（At-Most-Once）**的广播总线，不落盘、无 Ack、无重放；需要可靠投递应用 Redis Streams 或 Kafka | 第 17 章 |
| 「Erlang 是 Redis Pub/Sub 的替代」 | Erlang 是实现技术栈的替代，不是消息语义的替代（同样是内存即发即忘） | 第 17 章 |
| Prometheus 被当作「时序数据库」 | 它是完整的监控系统（采集+存储+查询+告警），且**单节点、不支持水平扩展** | 第 20 章 |

| 窗口类型列了 Tumbling / Hopping / Sliding / Session | Hopping 与 Sliding 是同一概念的两种叫法；主流为滚动 / 滑动 / 会话（+ 全局） | 第 21 章 |

## 第二节　逐章明细

## 第 1 章：从零到百万用户

### 勘误

1. **Master-Slave 是过时的术语**
   - 原文说法：全文使用「Master-Slave Model」「master database」「slave database」。
   - 正确说法：使用 Primary-Replica 或 Leader-Follower。MySQL 用 SOURCE/REPLICA、PostgreSQL 用 Primary/Standby、Kafka 用 Leader/Follower。这是沟通准确性问题，不是「政治正确」问题。

2. **消息队列不是「存在内存中」**
   - 原文说法：消息队列是持久化组件，存在内存中。
   - 正确说法：消息队列持久化到磁盘，高性能来自顺序写、页缓存、零拷贝。面试答「如何不丢消息」的链条是：生产者 ack → Broker 持久化并多副本 → 消费者手动提交 offset。

3. **主库故障转移的「数据恢复脚本」是过时做法**
   - 原文说法：选中的从库可能不是最新的，需要运行数据恢复脚本更新数据（多主和环形复制可能有帮助）。
   - 正确说法：用半同步复制保证至少一台副本已收到数据，用 GTID / LSN 做精确位点切换，用 Patroni / Orchestrator / MHA 自动故障转移。核心指标是 RPO 与 RTO。

4. **一致性哈希不能解决分片倾斜和名人问题**
   - 原文说法：重新分片和名人问题可以「用一致性哈希来克服」。
   - 正确说法：一致性哈希只解决「节点增减时数据重新分布的比例」问题。倾斜要靠预先规划大量逻辑分片 + 合理分片键；热点要靠缓存、key 加盐、热点数据单独分片。

5. **LRU 不是唯一值得知道的淘汰策略**

## 第 5 章：一致性哈希

### 勘误

1. **Introduction 声称一致性哈希「保证均匀分布」，与后文自相矛盾**
   - 原文说法：Introduction 写它「ensures an even distribution of data」。
   - 正确说法：一致性哈希保证的是「节点增减时迁移比例小」（约 1/N）。均匀分布不是它保证的，而是要靠虚拟节点去逼近。

2. **Mitigates Hotspots 的说法会误导初学者**
   - 原文说法：Benefits 一节写它「Balances data distribution to avoid server overload」。
   - 正确说法：它缓解的是分区倾斜导致的热点，不缓解热点 key——同一个 key 永远映射到同一节点。热 key 要靠缓存、key 加盐、热点数据单独分配节点。

3. **拼写与编号问题（表述层面）**
   - 原文说法：Key Concepts 编号重复（两个 1.）、虚拟节点一节把 distributed 拼成 distrubuted、serverIndex 命名与全文风格不一致。
   - 正确说法：编号应为 1→2→3，拼写应为 distributed，命名统一为 server_index。不影响技术正确性，但降低教程可信度。

### 补充

1. **节点少时的分布不均需要量化**
   - 要点：N 个随机节点时最大弧长期望约 (ln N + γ)/N，即最忙节点要扛平均值的 ln N + γ 倍（10 台 2.9 倍、100 台 5.2 倍）。这是「为什么必须用虚拟节点」的量化依据。

2. **虚拟节点数量的经验值**
   - 要点：负载相对标准差 ≈ 1/√V，给出 V=64/128/256/1024 的数值，以及 Cassandra 从 256 改到 16 的原因（元数据、修复、启动开销）。

3. **为什么是「顺时针」——这只是一个约定**
   - 要点：顺时针和逆时针在数学上完全等价，唯一要求是所有参与者约定一致。不要把任意约定当成算法组成部分。

4. **负载均衡与数据分区是两种不同的用法**
   - 要点：两类用法在重新映射代价、是否需要副本、故障处理上完全不同；数据分区场景还必须配合副本与 Quorum（原笔记完全缺失）。

5. **一致性哈希不是唯一解**
   - 要点：Rendezvous Hashing（HRW）、Jump Consistent Hash、Maglev Hashing 三个替代方案，含复杂度、内存、均匀性与适用场景对比（详见第 9 节）。

6. **一致性哈希的代价与前提**
   - 要点：它只决定映射关系、不负责搬数据；有元数据一致性、vnode 运维成本、新节点冷启动等代价。只讲收益不讲代价会被认为缺乏工程经验。

7. **真实系统的具体用法**
   - 要点：补充 DynamoDB、Cassandra、Discord、Akamai、Maglev 各自怎么用，以及 DynamoDB 与 Dynamo 论文需小心区分的地方（详见第 11 节）。

## 第 6 章：键值存储

### 勘误

1. **CAP 定理被简化成「三选二」，这个框架是错的**
   - 原文说法：开篇写「只能满足三个保证中的两个」，并把系统分为 CP、AP、CA 三类。
   - 正确说法：网络分区不是设计选项而是物理现实，P 是必选项。CAP 真正描述的是「分区发生时如何在 C 和 A 之间取舍」，现实中只存在 CP 与 AP，不存在 CA 系统。

2. **CAP 中的 C 不是「所有客户端看到同样的数据」**
   - 原文说法：把 Consistency 定义为「所有客户端同时看到相同的数据」。
   - 正确说法：CAP 的 C 指线性一致性——一旦某次写入返回成功，之后任何读取都必须看到这次写入，行为等价于单机系统。

3. **把「虚拟节点」和「数据中心故障」扯上了关系**
   - 原文说法：写「把副本放在不同数据中心，以在虚拟节点的情况下提高可靠性」。
   - 正确说法：应为 in case of node failures 或 data center outages。虚拟节点是一致性哈希环上的概念，与数据中心可靠性无关。

4. **W = 1 不等于「可能读到旧数据」**
   - 原文说法：写「W=1、R=N 时系统为快速写入优化」，读者会顺势理解为 W=1 就会读到旧数据。
   - 正确说法：W=1、R=N 时 W+R=N+1>N，依然满足强一致。W=1 需要警惕的是持久性风险。要读到旧数据必须 W+R ≤ N。

5. **术语笔误 vector locks**
   - 原文说法：小标题写「Versioning and vector locks are used to solve inconsistency problems」。
   - 正确说法：应为向量时钟（Vector Clock）。vector locks 不是一个存在的数据结构。

   - 要点：CAP 只描述分区时的取舍，PACELC 补上正常运行时的延迟与一致性权衡。是判断数据库真实行为特征的关键框架，也是面试加分点（详见第 2 节）。

2. **R + W > N 的推导与直觉**
   - 要点：原笔记只给结论没解释为什么。理解「读集合与写集合必然相交」的鸽巢原理推导，比记住公式重要得多（详见第 5 节）。

   - 要点：原笔记列了构建四步却没讲清为什么能减少传输量。这是本章最值得花时间理解的数据结构（详见第 7.3 节）。

   - 要点：原笔记混用两个概念。Dynamo 论文虽叫 vector clock，实质更接近版本向量（详见第 6 节）。

## 第 8 章：URL 短链

### 勘误

1. **布隆过滤器不能「解决」哈希冲突**
   - 原文说法：写「用布隆过滤器解决冲突，以实现高效查找」。
   - 正确说法：布隆过滤器只有假阳性没有假阴性，且不支持删除，是内存中的概率结构。它只能做前置过滤，真正的冲突裁决必须由数据库唯一索引承担。完整链路是：布隆过滤器预检 → 唯一索引兜底 → 冲突后重试（有上限）。

2. **「每个长 URL 映射到一个短码」不是唯一性的完整表述**
   - 原文说法：写「每个长 URL 必须哈希到一个哈希值」。
   - 正确说法：这句描述的是函数确定性，短链真正需要的唯一性是反方向的——短码 → 长 URL 一对一。同一长 URL 可允许多个短码，但一个短码绝不能对应两个长 URL。

3. **301 重定向的代价被严重低估**
   - 原文说法：把「减少服务器压力」呈现为 301 的主要优势，只说 302 适合统计点击。
   - 正确说法：301 还导致无法修改跳转目标、无法撤销恶意链接（安全问题）、点击数据严重失真。需要统计/风控/可撤销的场景必须用 302（或 307）。商业短链服务普遍使用 302。

4. **碰撞概率被隐性地低估了**
   - 原文说法：只说「取前 7 个字符会导致哈希碰撞」，没说有多频繁。
   - 正确说法：根据生日悖论，约 √M 次插入碰撞概率就超 50%。7 位十六进制字符（16^7）只需约 1.6 万条记录即过半。对每天 1 亿条的服务，碰撞是日常事件。

5. **Base 62 的数值全部正确（诚实说明）**
   - 原文说法：给出「7 个字符支持约 3.5 万亿个 URL」与示例 2009215674938 → zn9edcu。
   - 正确说法：两处都正确。补充原笔记未算出的关键结论：62^6 ≈ 568 亿小于所需的 3650 亿，所以必须用 7 位；7 位短码按每天 1 亿条可撑约 96.4 年。

1. **短链的安全与合规（钓鱼防护）**
   - 要点：短链是天然的开放重定向系统。补上目标 URL 扫描、预览页、域名信誉分级、创建侧风控、撤销能力、签名短码等方案（详见第 4.5 节）。

## 第 9 章：网络爬虫

### 勘误

1. **URL Frontier 不是「一个 FIFO 队列」**

   - 正确说法：它是多层队列系统，至少包含前队列（按优先级）与后队列（按主机名）。「FIFO 队列」只是对外的抽象接口。应把它理解成一个调度器，而非一个队列。

2. **「Queue Selector」一词被用于两个不同阶段，造成混淆**

3. **「哈希比对检测重复内容」只覆盖了精确重复**

4. **Crawl-delay 被当作标准指令**

## 第 10 章：通知系统

### 勘误

1. **只用一个 event ID 去重会导致大面积漏发**

1. **设备令牌（device token）的完整生命周期**

## 第 11 章：新闻信息流

### 勘误

1. **「按时间倒序」不是现代信息流的主流做法**
   - 原文说法：写「信息流按时间倒序排列，以求简单」。

2. **一致性哈希的定位被写偏了**
   - 原文说法：写「一致性哈希：把请求均匀分发到服务器」。
   - 正确说法：一致性哈希解决的是数据分片问题（key 放哪个节点），请求分发是负载均衡器的职责。两者是不同层次的机制。它也不解决热点问题。

1. **大 V 问题的量化**

2. **信息流排序的架构支持**
   - 要点：算法排序需要两阶段架构（候选生成 → 精排），依赖特征存储与在线模型服务；它会破坏信息流的可缓存性，这是最容易被忽略的代价（详见第 7 节）。

3. **分页必须用游标，不能用 offset**
   - 要点：信息流持续变化，offset 分页会导致重复和漏项。正确做法是基于游标（cursor）分页，用上一页最后一条的 ID/时间戳锚定（详见第 2.2 节）。

4. **不活跃用户优化与冷启动**
   - 要点：不活跃用户不推送是投入产出比最高的优化之一，在日活远小于月活的平台能直接砍掉大部分扇出量（详见第 4.4 节）。

### 补充

1. **SSE（Server-Sent Events）**
   - 要点：原笔记漏掉了 SSE。它是服务器单向推送的轻量方案，跑在普通 HTTP 上、浏览器自动重连、穿透防火墙强；适合通知、行情、大模型流式输出，不适合客户端高频发送的聊天（详见第 2.4 节）。

## 第 13 章：搜索自动补全

### 勘误

1. **查询流程自相矛盾（遍历子树 vs 不遍历）**
   - 原文说法：Query Processing Flow 写「遍历子树收集有效建议」，Optimizations 又写「在每个节点缓存 top-k 以避免重复遍历」。
   - 正确说法：两处互相矛盾。主路径是「走前缀 → 直接读节点缓存的 Top-K」（O(前缀长度 + K)）；遍历子树只作为兜底。

2. **「实时处理不现实」是过时的表述**
   - 原文说法：写「实时处理对大数据集不现实」，Trie 更新「很少实时，每周更新替换旧数据」。
   - 正确说法：「实时全量重建 Trie」确实不现实，但「实时更新建议」完全可行。用基础层 + 热点层的双层结构（Lambda 架构），热点词可在秒到分钟级进入补全。

3. **「限制前缀长度到 50」的数字和理由都不严谨**
   - 原文说法：写「把前缀长度限制到 50，因为用户很少输入长查询」。
   - 正确说法：50 很随意，真实分界点在 20–30 字符。真正原因是超过一定长度后建议基本收敛，且限制深度能给 Trie 大小设上界、控制内存。

4. **KV 存储方案被当成了等价选项，其实代价很大**
   - 原文说法：把 KV 存储和 Trie 并列成两种存储选项。
   - 正确说法：KV 方案会失去前缀共享（t、tr、tre 是三个独立 key），且每次查询是一次网络往返。KV 适合查询量不大、想快速上线的场景；自建 Trie + mmap 适合查询量极大、对延迟和成本敏感的场景。

### 补充

1. **节点缓存 Top-K 的细节与内存代价**
   - 要点：把「遍历子树 + 排序」降为「走前缀 + 读 K 条」；代价是内存（约 1 亿节点 × 5 × 4 字节 ≈ 2 GB）；浅层热节点必须缓存，深层冷节点选择性缓存（详见第 3.2 节）。

2. **Trie 的内存优化四招**
   - 要点：双数组 Trie、前缀压缩（Radix Tree，节点数减少 50%–90%）、序列化 + mmap（无指针扁平文件，进程间共享、按需加载、零 GC）、KV 存储方案（详见第 5 节）。

3. **流式实时性（双层 Trie / Lambda 架构）**
   - 要点：基础层天级批量重建保证全和准，热点层秒/分钟级流式更新保证快，查询时合并；用 Count-Min Sketch 省内存，时间衰减自动过期，写入幂等（详见第 8 节）。

4. **个性化与隐私**
   - 要点：个性化分全局/群体/个人三层；个人层绝不能写进全局 Trie；共享设备、敏感查询、名誉侵权、搜索投毒都是真实风险（详见第 9 节）。

5. **过滤层与 Top-K 缓存的交互（超额取）**
   - 要点：若节点缓存 Top-5 中 2 条被黑名单过滤，用户只看到 3 条。解法是节点缓存 Top-(K+F)，过滤后返回前 K 条，F 按历史过滤率动态调整（详见第 3.3 节）。

6. **QPS 48,000 的推导**
   - 要点：1000 万 DAU × 10 次搜索 × 20 次按键 = 20 亿请求/天 → 平均 23,148 QPS → 峰值（2 倍）≈ 46,296 ≈ 48,000。峰值倍数只有 2 倍，因为搜索行为分散在全天（详见第 1 节）。

   - 正确说法：HDS 依赖 Flash，Flash 已于 2020 年 12 月全面停止支持。当前主流是 HLS 和 DASH，另有 LL-HLS / LL-DASH。现代流媒体完全建立在普通 HTTP 之上。

## 第 15 章：Google Drive 设计

### 勘误
1. **「500 PB 总存储」没有推导，按字面算不出来**
   - 原文说法：10M DAU × 10 GB 免费空间 = 500 PB。
   - 正确说法：`1000 万 × 10 GB = 100 PB`，只有五分之一。要得到 500 PB 需补齐约 2 倍版本历史 × 2.5 倍冗余。更值得记的是用户配额（100 PB）与真实占用（约 3.65 PB/年）差近 30 倍——云盘商业模型建立在**配额超卖**之上。

2. **「First processed version wins」用词有严重误导性**
   - 原文说法：冲突时「先被处理的版本胜出」，同时又说冲突版本单独保存。
   - 正确说法：应表述为「服务端版本保留原文件名，客户端版本另存为带冲突标记的新文件」（保留双副本）。判定冲突靠**因果关系**而非时间戳，须用**版本向量**；LWW 会静默丢数据，只适用于在线状态这类可丢数据。

3. **「Master-Slave」是过时的术语**
   - 原文说法：`Promote a slave node to master`。
   - 正确说法：改用 **Primary-Replica** 或 **Leader-Follower**（MySQL `SOURCE/REPLICA`、PostgreSQL `Primary/Standby`、Kafka `Leader/Follower`）。

4. **主库故障「提升副本」与本系统核心约束冲突**
   - 原文说法：Metadata DB 故障时提升 slave 为 master 并重定向流量。
   - 正确说法：异步复制下被提升的副本可能落后，未复制的写入永久丢失，违反「数据丢失不可接受」。须用**半同步复制 + GTID/LSN 位点切换 + 自动故障转移**（Orchestrator / Vitess / Patroni），并接受写延迟——这是 RPO=0 的必然代价。

### 补充
1. **块级同步与内容定义分块（CDC）**：原笔记只有一句「只传变化的块」。固定 4 MB 分块下，文件开头插入一字节会导致 100% 重传；CDC 能把重传量压到 5% 以下。
2. **rsync 滚动校验和算法**：核心是弱校验和的**增量可更新性**，把滑动窗口代价从 O(w) 降到 O(1)。
3. **通知服务的四种机制与容量估算**：没有一种机制覆盖所有场景（WebSocket / SSE / 长轮询 / 移动推送混合）；通知只能作**提示**，绝不能承载数据（不可靠 vs 拉取幂等）。
4. **存储成本优化的三个隐藏矛盾**：去重 / 加密 / 隐私三者只能取其二；冷存储取回有分钟到小时延迟；纠删码比三副本省一半以上但恢复更慢。
5. **命名空间模型无法支撑「分享」**：「路径唯一标识」打破了「一个文件只属于一个用户」的假设；真实云盘转向**「文件 ID + 父子引用」的图模型**。
6. **`pending` 状态机与块引用计数**：缺状态机会让用户下载到不完整文件且不报错；缺引用计数会误删仍被引用的块——自研云盘最常见的数据丢失事故来源。
7. **压缩必须在加密之前**：加密后数据几乎不可压缩，顺序搞反会让存储与带宽成本悄悄翻倍且不报错。

## 第 16 章：Proximity Service（附近服务）

### 勘误
1. **二维范围查询的 SQL 单位错误——用「度」减「米」**
   - 原文说法：`WHERE latitude BETWEEN :lat - radius AND :lat + radius`。
   - 正确说法：`radius` 单位是米、经纬度是度，`:lat - radius` 会覆盖整个地球。须除以 `111320`，**经度还要乘 `cos(纬度)`**（北纬 60° 处漏掉会少一半结果）。另注意**包围盒 ≠ 圆**，须用 Haversine 做第二阶段精筛。

2. **搜索 QPS 的算术有偏差**
   - 原文说法：`(100M × 5) / 86,400 ≈ 5,000 QPS`。
   - 正确说法：`5 亿 / 86,400 ≈ 5,787`，约 **5,800 QPS**；更重要的是必须再乘 2~3 倍峰值系数 → 峰值约 **1.2 万~1.7 万 QPS**。

3. **GeoHash 半径映射表中「20 km → 长度 4」是边界情况**
   - 原文说法：参考表给出 `20 km → geohash length = 4`。
   - 正确说法：长度 4 格子纬度方向仅约 19.6 km，小于搜索半径。应改用长度 3，或保持长度 4 但把邻域从 3×3 扩到 **5×5**（实践中更合理）。表中前四项均正确。

4. **「GeoHash 保证共享前缀越长越近」需补上逆命题不成立**
   - 原文说法：前缀越长越近。
   - 正确说法：应明确为**单向保证**——「前缀相同 ⇒ 位置相近」成立，「位置相近 ⇒ 前缀相同」不成立。反例：相邻格子只共享 5 个字符；赤道两侧相距约 22 米的点可能零共享前缀。必须查询相邻 8 个格子。

5. **Quadtree 小节内容准确，无技术错误**
   - 核查结果：逐条验算通过（约 267 万节点、GB 级内存、O(n log n) 构建、三条运维注意事项均成立）。补充：四叉树核心优势是**自适应密度**，核心劣势是**写代价高**，最适合每天批量更新的场景——恰好匹配本章需求。

### 补充
1. **GeoHash 精度的完整验算表**：6 位 geohash ≈ 1.22 km × 0.61 km（赤道）；经度宽度随纬度收缩；12 个层级从 5000 km 细分到 3.7 cm。
2. **GeoHash 的边界问题及解决方案**：原笔记只说「需搜索相邻格子」，没说清严重程度与完整解法——本章最易被追问的点。
3. **Redis GEO 与 PostGIS 的工业实现**：Redis GEO 底层是 ZSET（score 为 52 位 GeoHash 整数）；PostGIS 默认 GiST 索引，行为等价于 R 树。
4. **Uber H3 与「六边形网格」的价值**：正方形网格的角邻居距离 1.41 格会造成方向偏差；六边形 6 个邻居等距，更适合逐环扩展。
5. **位置数据的隐私合规与工程对策**：假名化 ≠ 匿名化；客户端把坐标吸附到 geohash 格子中心可同时解决性能与隐私；中国 PIPL 将「行踪轨迹」列为敏感个人信息，需**单独同意**。
6. **最终检索流程缺少「精筛」和「限制条数」**：须过滤包围盒四角误报并限制返回条数（市中心 500 米内可能有几千家餐厅）。
7. **缓存键用 geohash 的深层原因**：本质是**量化（Quantization）**——把连续值离散化，让缓存键稳定、从而能命中。

## 第 17 章：Nearby Friends（附近的朋友）

### 勘误
1. **Redis Pub/Sub 的「即发即忘」语义完全没有被说明**
   - 原文说法：把 Pub/Sub 描述为「轻量级消息总线」。
   - 正确说法：它是**至多一次（At-Most-Once）**投递——不落盘、无确认、无重放、无消费者组，订阅者不在线消息就永久丢失。它是**广播总线**而非消息队列；本场景因允许偶尔丢点而适用，但正确性依赖 Redis 位置缓存兜底。

2. **「每秒 1400 万次位置更新」是概念混淆**
   - 原文说法：`push ~14mil location updates per second`。
   - 正确说法：那是**扇出后的推送消息数**（33.4 万 × 40 ≈ 1333 万），不是位置更新数。须严格区分：上报量 33.4 万/秒、扇出量约 1333 万/秒、订阅关系总数约 40 亿——三者对应完全不同的资源。

3. **「为所有用户预分配 Pub/Sub 频道」基于对 Redis 语义的误解**
   - 原文说法：预分配频道以避免上线时创建新频道。
   - 正确说法：Redis 频道**隐式存在**，`SUBSCRIBE` 自动创建、最后一个订阅者离开自动销毁，没有「预分配」操作。真正要预分配并缓存的是**「频道 → Redis 节点」的归属映射**（哈希环分布）。

4. **把 Erlang 当作 Pub/Sub 的语义替代品不准确**
   - 原文说法：用 Erlang 在同一应用里处理 WebSocket 与 Pub/Sub。
   - 正确说法：Erlang 的进程消息同样是内存中、即发即忘，**没有解决任何持久性或丢失问题**。它是**实现技术栈的替代**，不是消息语义的替代；要修丢消息应用 Redis Streams 或 Kafka。

### 补充
1. **位置上报的节流策略**：距离阈值 + 最小间隔 + 最大间隔心跳三者组合——初级开发者最易做错的工程细节。
2. **位置隐私与三角定位防护**：模糊化必须在**服务端**做；时间窗内噪声必须一致（否则会被平均掉）；按查询者加盐防多账号合谋；历史轨迹须降精度。
3. **扇出合并推送（Batching）**：按 5 秒窗口合并，可把扇出量从 1333 万/秒降到 200 万/秒（降低 6.7 倍），代价是消息最多延迟 5 秒。
4. **推送 + 拉取兜底**：给每条更新带版本号，客户端发现断档就主动拉快照——弥补 Pub/Sub 丢失问题的标准解法。
5. **距离阈值的滞回设计**：用「显示半径 5 英里 + 推送半径 6 英里」的双半径消除阈值抖动。
6. **Redis 7.0 的分片 Pub/Sub**：`SSUBSCRIBE` / `SPUBLISH` 让消息只在持有该频道的分片内传播，大规模集群必知。

## 第 18 章：Google Maps 设计

### 勘误
1. **地图瓦片用的是 Z/X/Y 索引，不是 geohash**
   - 原文说法：`Map tiles are served statically, based on their geohash`。
   - 正确说法：瓦片用 **Z/X/Y 三级索引**（Web Mercator 平面四叉树），geohash 在 WGS84 经纬度上做四叉树切分。瓦片格子必须是**正方形**以便无缝拼接。判断标准：要「一张图」用 Z/X/Y，要「一组点」用 geohash。

2. **Web Mercator 的「modified」没有解释，容易导致误用**
   - 原文说法：Google Maps 选择了 Mercator 的变体 Web Mercator。
   - 正确说法：**EPSG:3857 是投影坐标系，单位是「伪米」**，水平尺度因子 `1/cos φ`、面积尺度因子 `1/cos² φ`（纬度 60° 放大 4 倍、85° 放大 131 倍）。算距离必须在 **EPSG:4326 经纬度上用 haversine**。这就是格陵兰岛看起来比非洲大的原因。

3. **「地理编码数据库用 Redis 存 KV」过于简化**
   - 原文说法：用 Redis 存经纬度与地点的 KV 对。
   - 正确说法：只覆盖**反向地理编码**（坐标→地址）。**正向地理编码**（地址→坐标）需要全文检索、模糊匹配、多语言消歧，须用**倒排索引**或专用引擎（Nominatim / Pelias）。

4. **「推送通知不支持 Web 应用」已经过时**
   - 原文说法：推送通知对 Web 应用不可用。
   - 正确说法：**Web Push 早已标准化**。结论（不用推送做导航）仍对，但理由应换为：延迟不可控、可靠性不足、载荷受限（约 4 KB）。「结论对但理由过时」是很隐蔽的错误。

5. **「每天 2500 万次实时位置更新」与本章自己的量级估算差 4 个数量级**
   - 原文说法：`25mil updates daily of real-time location info`。
   - 正确说法：按本章自身估算约 200 亿次/天，差约 800 倍。更合理的解释是它指「每天 2500 万次**地图数据更新**」，但**原文没有说明统计口径**，口径不清的数字不能用于容量规划。

6. **路线规划只提「Dijkstra 或 A\* 的变体」，遗漏了真正的答案**
   - 原文说法：大多数导航算法用 Dijkstra 或 A\* 的变体。
   - 正确说法：现代做法是 **Contraction Hierarchies（CH）** 或 **CRP**，加速比约 500~1000 倍。纯 Dijkstra 不可用的本质是**经济上不成立**：美国路网 2394 万节点，20 万 QPS 需约 40 万 CPU 核、每小时约 1.2 万美元。

7. **约 70 PB 这个数字需要说明推导口径**
   - 原文说法：`estimated as ~70pb based on all the tiles we need to store`。
   - 正确说法：70 PB 是**实际存储量**，不是理论瓦片总量。Z=0~21 共约 5.86 万亿块，即使每块 5 KB 也是约 29,000 PB。差距来自去重、矢量瓦片、按需生成三项优化。

### 补充
1. **Z/X/Y 瓦片坐标体系与缩放级别规律**：`X = floor(n × (lon + 180) / 360)`（Y 轴向下）；瓦片总数 `= 4^Z`，每加一级 ×4；Z=21 时一块瓦片在赤道仅 19.1 米宽。
2. **路线规划算法的完整演进**：Dijkstra → A\* → ALT → Highway Hierarchies → CH → CRP，及各自加速比与适用场景——本章最需补充的技术内容。
3. **实时路况的数据来源与更新频率**：五类数据源、分钟级更新；探针不足时应**回退到历史模型**（按星期几 + 时段）。
4. **地图数据的分层存储与增量更新**：七个图层、更新频率相差 6 个数量级必须分开存；六种增量更新手段（版本号、影响分析、版本化 URL、条件请求、预取、原子切换）。
5. **矢量瓦片 vs 栅格瓦片**：它是一次架构级选择，最大价值不是省带宽而是**数据与样式解耦**。
6. **地图数据建模的图论细节**：边权重是**通行时间**而非距离、转弯代价、有向图（单行道）、立交桥上下层不连通。

## 第 19 章：Distributed Message Queue（分布式消息队列）

### 勘误
1. **`replica.lag.max.messages` 已被移除十年**
   - 原文说法：用「副本落后多少条消息」判定是否在 ISR 中。
   - 正确说法：该参数在 **Kafka 0.9.0.0（2015 年）就被移除**。用条数衡量不合理（流量暴涨时健康副本会被误判踢出 ISR）。现代 Kafka 用 **`replica.lag.time.max.ms`**，基于时间判断（默认 30 秒）。

2. **消费者偏移量不存在 ZooKeeper 里**
   - 原文说法：消费者状态适合放在 ZooKeeper。
   - 正确说法：**从 Kafka 0.9 起不再成立**。ZK 每次写都走共识（Zab），扛不住高频小写入。偏移量存在 Kafka 内部主题 **`__consumer_offsets`**，用**日志压缩**只保留最新值。

3. **副本分配方案不是分区 Leader 决定的**
   - 原文说法：分区 Leader 创建副本分配方案并存入 ZK。
   - 正确说法：分区 Leader 负责数据复制与读写服务；决定副本放在哪些 Broker 上的是 **Controller**（ZK 模式写 ZK、KRaft 模式写元数据日志）。

4. **HDD 顺序读写「几 MB/s」严重低估**
   - 原文说法：`HDDs can achieve several MB/s`。
   - 正确说法：现代 7200 RPM HDD 顺序读写 **150~250 MB/s**，是「几 MB/s」的几十倍。机械盘**随机**访问才慢（IOPS 100~200），顺序访问能接近盘片理论带宽——这正是「追加日志替代随机更新」的全部理由。

5. **`ACK=all` 的写法与理解都要修正**
   - 原文说法：用 `ACK=all` 并把持久性完全归因于该参数。
   - 正确说法：参数名是 **`acks`**（小写复数），取值 `0`/`1`/`all`。持久性由 **`acks` + `replication.factor` + `min.insync.replicas`** 共同决定；还要知道 `unclean.leader.election.enable`（默认 false）。

### 补充
1. **KRaft 与 ZooKeeper 的演进（原笔记完全缺失）**：Kafka 2.8 引入、3.3 生产可用、**4.0 已彻底移除 ZK 依赖**；还说「Kafka 用 ZK 存元数据」会立刻暴露知识陈旧。

## 第 21 章：Ad Click Event Aggregation（广告点击事件聚合）

### 勘误
1. **把「允许迟到时间」误称为水位线（Watermark）**
   - 原文说法：窗口延长出来的部分就叫做 watermark。
   - 正确说法：水位线是**进度信号**（表示事件时间早于 T 的事件不会再来了），决定窗口**何时触发**；「把窗口往后延长一段」叫**允许迟到时间**（Allowed Lateness），决定触发后**还能收多久**。正确三层表述：水位线 → 允许迟到 → 侧输出流。

2. **窗口类型分类混乱，Hopping 与 Sliding 是同一个东西**
   - 原文说法：并列列出 Tumbling、Hopping、Sliding、Session 四种。
   - 正确说法：Hopping 与 Sliding 是同一概念的两种叫法（Flink 叫 Sliding、Azure Stream Analytics 叫 Hopping）。主流为三类：滚动 / 滑动 / 会话（外加全局）。`Size == Slide` 即滚动窗口——**滚动窗口是滑动窗口的特例**。

3. **把「按维度预聚合」称为星型模型（Star Schema）**
   - 原文说法：按 country 等维度预聚合「这个技术叫做 star schema」。
   - 正确说法：**星型模型是数据建模术语**（事实表 + 多个维度表），回答「数据怎么组织」；原文描述的是**预聚合 / 数据立方体 / 物化视图**，回答「结果怎么算」。原文的表可作为星型模型的事实表，但两者是配合关系。

4. **Kappa 架构的判定依据不严谨**
   - 原文说法：因为重算也走聚合服务，所以是 Kappa 架构。
   - 正确说法：Kappa 的关键特征是**「重放可保留的日志」**，而不是「从冷存储跑批任务」。原文的重算从冷存储读、是独立批任务，更像 Lambda 的批处理层。准确描述是「混合架构」或「以 Kappa 思想实现的架构」。

5. **投递语义的表述不完整**
   - 原文说法：通过第二个消息队列实现「端到端 exactly-once atomic commit semantics」。
   - 正确说法：「恰好一次**投递**」在网络层不可能实现。准确表述是 **Exactly-Once Processing** 或 **Effectively-Once**——由「状态恰好一次（检查点）+ 输出恰好一次（两阶段提交 / 幂等 Sink）」组合而成，需链路上每一环配合。

### 补充
1. **Lambda 与 Kappa 的完整对比**：Lambda = 两套代码；Kappa = 一套代码、靠重放日志；演进动因是现代流处理引擎补齐了正确性能力。
2. **时间语义的完整体系**：原笔记只讲了事件时间 vs 处理时间的取舍。记忆链：事件时间 → 乱序 → 水位线 → 允许迟到 → 侧输出流 → 日终对账。**本章最重要的补充内容**。
3. **业务级数据去重（原文完全缺失）**：同一用户对同一广告的重复点击该不该计费——重复点击 = 多收广告主钱 = 商业欺诈。含三种方案对比与内存成本推算（1.8 亿 key → 布隆 216 MB vs Redis SET 20~30 GB）。
4. **对账（Reconciliation）的完整机制**：对账的具体做法、阈值怎么定、发现差异怎么办；**阈值必须由业务方定义**。
5. **Flink 的端到端恰好一次实现**：检查点（Chandy-Lamport 快照）+ 两阶段提交 Sink + 幂等写入三条路径；下游幂等是最便宜的解法。
6. **背压（Backpressure）**：流处理系统最常见的故障模式。Flink 用基于信用的流控；Kafka 没有真正背压，只能靠监控 lag + 自动扩容。背压是**症状**不是病因。

## 第 22 章：Hotel Reservation System（酒店预订系统）

### 勘误
1. **CHECK 约束与「允许超卖 10%」的需求自相矛盾**
   - 原文说法：需求允许超卖 110%，约束却是 `CHECK(total_inventory - total_reserved >= 0)`。
   - 正确说法：该约束等价于「已预订不超过 100%」，会直接禁止超卖。应为 `CHECK (total_reserved <= total_inventory * 1.1)`，更规范的做法是**把超卖比例参数化**（按酒店/房型/季节配置），而非硬编码 `1.1`。

2. **扣减库存的 UPDATE 语句漏掉了 `hotel_id` 过滤条件**
   - 原文说法：`WHERE room_type_id = ? AND date BETWEEN ? AND ?`（前一步 SELECT 却有 `hotel_id`）。
   - 正确说法：`room_type_id` 只在酒店内唯一，该语句会误扣**所有酒店**的库存，是资金损失级 bug。必须补 `AND hotel_id = ?`；防呆手段包括让主键为 `(hotel_id, room_type_id, date)`、开启 `sql_safe_updates`、先 SELECT 验证影响范围。

3. **`room_type_rate` 表缺少 `room_type_id` 列，无法存储分房型价格**
   - 原文说法：字段为 `hotel_id`(PK)、`date`(PK)、`rate`。
   - 正确说法：名为「房型价格」却无房型字段，同一酒店同一天只能有一个价格，无法表达「标准房与套房价格不同」。主键应为 `(hotel_id, room_type_id, date)`——与 `room_type_inventory` 结构一致。

4. **`status` 字段的归属描述错误**
   - 原文说法：`status` 代表**某个房间**的状态机。
   - 正确说法：从状态图（Pending→Paid/Canceled/Rejected、Paid→Refunded）看，它是**预订（reservation）**的状态机。每个状态转换都对应一次业务动作（释放预占、退款、加回库存），且必须幂等、须有明确不变量。

5. **把 CHECK 约束描述为「与乐观锁非常相似」是不准确的**
   - 原文说法：该方案和乐观锁非常相似，只是守卫换成了数据库约束。
   - 正确说法：并发行为相反——乐观锁冲突时影响 0 行、应用层失败重试；`UPDATE + CHECK` 靠 InnoDB 行锁**阻塞排队**、不重试，更接近**悲观锁**。CHECK 约束是**安全网**，不是并发控制机制。另注意 MySQL 8.0.16 之前会**静默忽略** CHECK 约束。

6. **缺少「检查后使用（TOCTOU）」问题的命名与原子解法**
   - 原文说法：准确描述了竞态并给出三个基于锁/约束的解法。
   - 正确说法：该问题通用名称是 **TOCTOU（Time-of-Check to Time-of-Use）**。最简洁解法是**原子条件更新**——把检查条件写进 `UPDATE ... WHERE ... AND total_reserved + n <= total_inventory * 1.1`，再检查 `affected_rows`，比悲观锁轻、比乐观锁简单、比约束可控。

### 补充
1. **Redis 分布式锁与 Redlock 争议**：酒店场景不推荐 Redis 锁（多一层故障点、无性能收益、正确性难保证）；Redlock 因依赖时钟假设、缺 fencing token 受质疑；Redis 官方文档也建议配合 fencing token。
2. **库存预占与「15 分钟超时释放」的实现**：`total_reserved` + `total_held` 双字段；延迟任务四种实现取舍；推荐「延时队列（准时）+ 兜底扫描（不漏）+ 释放逻辑幂等（防重复）」。
3. **分布式事务的完整对比（TCC、本地消息表）**：2PC / TCC / Saga / 本地消息表四种方案在一致性、性能、业务侵入性三个维度的取舍。
4. **搜索与预订的一致性**：问题有三层成因，其中「用户思考的时间差」物理上无法消除；四层缓解策略（预占 / 短 TTL + CDC / 前端兜底 / 异步排队）。核心原则：**缓存可以不准，数据库必须准**。
5. **价格缓存策略（与库存缓存的区别）**：价格与库存的变化频率、错误后果完全不同——库存用短 TTL + CDC 失效，价格用长 TTL + 每日定时刷新 + 随机抖动 + 预取。
6. **幂等的三层实现模式**：唯一约束 / 幂等键表 / 状态机条件更新；并区分**幂等 ≠ 去重**——幂等是更强的性质，也更容易实现。

## 第 23 章：Distributed Email Service（分布式邮件服务）

> 本章原笔记整体结构清晰、结论可靠，估算部分经复算全部正确。以下为表述含糊、内容缺失或需要限定之处。

### 勘误
1. **POP3「取走即删除」是默认配置，不是协议强制**
   - 原文说法：Once retrieved, emails are deleted from remote server。
   - 正确说法：POP3 默认 `RETR` 后删除，但客户端可选择**保留副本**。真正淘汰 POP3 的原因是**状态在客户端**——不支持服务端文件夹、已读标记、搜索，多设备必然出问题。IMAP 也不是终点，现代替代是 **JMAP（RFC 8620/8621）**。

2. **送达率部分漏掉了 DMARC，且未涵盖 2024 年的行业强制要求**
   - 原文说法：只提 SPF 和 DKIM。
   - 正确说法：**没有 DMARC，SPF 和 DKIM 无法阻止伪造显示名（`From:` 头）**。完整验证是 **SPF + DKIM + DMARC 三位一体**，DMARC 负责对齐检查、失败处置策略与报告回传。**2024 年 2 月起** Google/Yahoo 对批量发信人强制要求三件套 + 一键退订（RFC 8058）、投诉率 < 0.3%。

3. **「使用专用 IP」并非对所有发信方都更好**
   - 原文说法：`use dedicated IPs ... otherwise recipient servers will not trust you`。
   - 正确说法：结论过于绝对。专用 IP 需发信量足够大才能积累信誉；小量发信时「冷 IP」送达率往往不如信誉良好的共享 IP。正确判断：**发信量大 → 专用 IP；发信量小 → 共享 IP**。

4. **「Elasticsearch 只能扩展到一定程度」需要限定**
   - 原文说法：ES scales to some extent，自研可 scale further。
   - 正确说法：生产 ES 集群可做到几十到上百节点、PB 级。不用它的真实理由是**运维成本和资源开销**（独立有状态服务、分片规划、JVM 堆开销），不是扩展性不够。

### 补充
1. **反垃圾邮件的完整机制**：分层拦截、贝叶斯过滤、发信人信誉、灰名单——设计邮件系统必须掌握的部分。
2. **退信处理（硬退信 / 软退信）**：`4xx` 软退信重试、`5xx` 硬退信永久移除；**不清理硬退信地址会直接摧毁域名信誉**。
3. **邮件搜索的底层结构**：倒排索引、分词、增量索引，以及「为什么不能用 `LIKE '%x%'`」。
4. **附件与正文分离存储的设计理由**：元数据「小、读多、要强一致」，附件「大、写一次读多次、要便宜」——访问模式不同的数据混在一起只会互相拖累。
5. **Cassandra 的一致性是可调的**：通过读写法定人数满足 `R + W > N`（如 3 副本下 QUORUM 读 + QUORUM 写）获得强一致性，代价是可用性下降。
6. **邮件传输安全**：STARTTLS（可被降级攻击）、MTA-STS（RFC 8461，强制 TLS）、TLS-RPT（RFC 8460，失败报告）；这些只保护传输中的邮件，端到端加密（S/MIME、PGP）是另一回事。

## 第 24 章：S3-like Object Storage（类 S3 对象存储）

4. **「对象存储是强一致的」需要补上一个关键时间点**
   - 原文说法：对比表 `Consistency: Strong consistency`。
   - 正确说法：**S3 的数据一致性模型在 2020-12-01 发生根本变化**。之前覆盖写与 DELETE 是最终一致的；之后所有 GET/PUT/LIST 及标签、ACL、元数据变更**全部强一致**，且不额外收费、对性能无影响。影响：EMRFS Consistent View / S3Guard 不再需要、数据湖可直接读刚写入的数据、`LIST` 后立刻 `GET` 安全。注意「S3 强一致」≠「所有对象存储强一致」。

### 补充
1. **预签名 URL（Presigned URL）——原笔记完全缺失**：原笔记的上传流程让客户端字节流经 API 服务中转（传 10 GB 搬 20 GB），大文件场景不可接受。预签名 URL 实现「控制面签发凭证、数据面直连」。
2. **分片上传的工程细节**：分片大小受 10000 上限约束（`分片大小 ≥ 文件大小 ÷ 10000`）、断点续传依赖服务端 `ListParts`、并行上传绕过单 TCP 的 RTT 限制、未完成分片必须配生命周期规则清理。
3. **元数据存储的扩展性**：为什么元数据是瓶颈（全局共享命名空间、访问量与请求数成正比、随机访问、强一致约束），以及业界做法（分片 + 一致性哈希 + 多层缓存 + 读写分离 + 反范式列举表 + 分层存储）。
4. **ETag 的陷阱**：分片上传对象的 ETag 是「各分片 MD5 拼接后再取 MD5」并带 `-N` 后缀，不等于整个对象的 MD5，不能用于整体校验、跨上传方式比对或去重。
5. **垃圾回收的完整机制**：垃圾占比阈值、引用计数、生命周期策略、反向孤儿清理。
6. **纠删码的进阶话题**：修复放大、LRC（局部可修复码）、为什么常见配置是 8+4 / 10+4 而非 20+4、以及**纠删码不能替代备份**（防硬件故障，不防误删除和软件 bug）。

## 第 25 章：Real-time Gaming Leaderboard（实时游戏排行榜）

> 原笔记整体结构清晰、判断基本正确，但在几处数字、命令和结论上存在可核实的问题。

### 勘误
1. **量级估算里的 DAU 前后不一致**
   - 原文说法：需求澄清写「5mil DAU and 25mil MAU」，量级估算却写「With 50mil DAU」。
   - 正确说法：两处差 10 倍。从「50 users per second」反推，`5,000,000 ÷ 100,000 = 50`，正确值是 **500 万 DAU**。

2. **把「到达率」当成了「同时在线人数」**
   - 原文说法：`peak online users would be 250 users per second`。
   - 正确说法：`DAU ÷ 秒数` 是**到达率（人/秒）**，不是同时在线人数。两者靠**利特尔法则**联系：并发数 = 到达率 × 平均停留时长（若平均在线 10 分钟，约 3 万人）。容量规划看并发数，QPS 规划才看到达率。

3. **关系型数据库「性能不好」的说法不准确**
   - 原文说法：`ORDER BY score DESC` 全表排序 makes a table scan。
   - 正确说法：有 `score` 索引时 `ORDER BY score DESC LIMIT 10` 是高效的（O(log N + 10)）。真正的瓶颈是**排名查询**（`COUNT(*) WHERE score >= X` 要扫过约一半索引条目）和**高频更新的索引维护成本**。

4. **每条记录 26 字节的估算漏了两件事**
   - 原文说法：`ID is 24-character string and score is 16-bit integer ... 26 bytes * 25mil = ~650MB`。
   - 正确说法：Redis 分数是 **8 字节双精度浮点**，且完全忽略了 Redis 内部开销（哈希表节点、SDS 头、跳表节点，约 120~150 字节/成员）。2500 万成员实际约 **3~3.5 GB**，5 亿成员约 **65 GB**。

5. **`INFO keyspace` 拿不到 sorted set 的成员数**
   - 原文说法：`total records per shard can quickly be accessed via the info keyspace command`。
   - 正确说法：`INFO keyspace` 返回的是**数据库里 key 的数量**，不返回 sorted set 成员数。正确命令是 **`ZCARD key`**（O(1)）——结论对，命令错。

6. **Redis Cluster 不是代理，也不是一致性哈希**
   - 原文说法：`It is a proxy which distributes data ... similar to consistent hashing`。
   - 正确说法：① 它是**去中心化**集群，节点间用 Gossip 交换状态，客户端靠 `MOVED`/`ASK` 重定向直连，**没有代理进程**；② 它用 **16384 个固定哈希槽**（`CRC16(key) mod 16384`），是确定性哈希，**没有哈希环、没有虚拟节点**。

7. **哈希分片下「无法确定用户排名」不成立**
   - 原文说法：`There is no straightforward approach to determine a user's rank`。
   - 正确说法：用 `rank(u) = 1 + Σ_i ZCOUNT(shard_i, "(score(u)", "+inf")` 可精确算出全局排名。结论（推荐按分数范围分区）不变，但**理由要换**——是「扇出成本随分片数增长、尾延迟受最慢分片拖累」，而不是「算不出来」。

### 补充
1. **`ZREVRANGE` 已被废弃**：Redis 6.2 起推荐 `ZRANGE ... REV`；`ZRANK`/`ZREVRANK` 在 Redis 7.2+ 支持 `WITHSCORE`。
2. **`ZRANK` 不返回并列名次（与需求矛盾）**：需求说「同分名次相同」，`ZRANK` 返回的是序列位置。正确做法是 `1 + ZCOUNT(key, "(myScore", "+inf")`——本章最重要的一处实现级错误。
3. **全局聚合排名的完整算法**：按分数范围（Σ 更高分片 `ZCARD` + 本分片 `ZCOUNT` + 1）、按哈希（Σ 所有分片 `ZCOUNT` + 1，精确但扇出 N 次）、精英榜 + 全量榜（头部精确、其余百分位近似）。
4. **分桶排名不会降低渐近复杂度**：很多资料说「分桶能把排名查询降到 O(1)」是**错的**；分桶的价值是分散内存与写入压力、让 Top-K 只读顶部桶。
5. **实时性与一致性的三层分解**：写入路径（写扩散 vs 定时重算）、读取路径（缓存与副本延迟）、跨地域。
6. **防作弊的分层设计**：信任边界、身份认证、请求完整性（签名 + nonce 防重放）、服务端复算、合理性校验、统计检测、限流。
7. **持久化的真实保证与重建方式**：Redis 主从复制默认**异步**；建议维护只追加的 `score_events` 表重建，而非解析脆弱的 binlog。

## 第 26 章：Payment System（支付系统）

> 原笔记覆盖了主要环节，`payment_order_id` 作幂等键、金额用字符串、复式记账、对账、重试退避、DLQ 等判断都是对的。但在「恰好一次」的表述、数据模型的合规性与若干工程细节上存在问题或缺失。

### 勘误
1. **「恰好一次投递」是一个不可实现的目标**
   - 原文说法：`An operation is executed exactly-once if it is executed at-least-once and at-most-once at the same time`。
   - 正确说法：结论（支付不能被处理两次）对，但「恰好一次**投递**」是**两将军问题**的直接推论，不可能实现——你无法区分「请求没到」和「扣了钱但响应丢了」。工程上追求 **At-least-once + 消费端幂等 = Effectively-once**，靠三层幂等（客户端幂等键、`payment_order_id`、PSP nonce）+ 对账兜底。

2. **`payment_events` 表里的 `credit_card_info` 与合规要求矛盾**
   - 原文说法：访谈说不在系统里存信用卡数据，数据模型却列了 `credit_card_info`。
   - 正确说法：自相矛盾——真存卡数据就进入 PCI DSS 最高审计范围（SAQ D）。该列应只存 **PSP 返回的支付方式令牌（token）** 和展示用元数据（卡组织品牌、后 4 位、有效期），字段名可改为 `payment_method_token`。边界在于「卡数据有没有**经过**你的系统」，不在于「有没有落库」。

3. **账本与钱包的更新顺序反了**
   - 原文说法：先更新钱包，后记账本。
   - 正确说法：复式记账体系中**账本是账簿（Book of Record），钱包只是物化视图**。先更新钱包会导致账本写入失败时账对不平且无法自动修复。应**先写账本**（原子插入借贷平衡分录），再用 `journal_id` 做幂等键**投影到钱包**。通用心智模型：先写事实、再更新缓存。

4. **「用 Paxos / Raft 保证副本始终同步」混淆了两件事**
   - 原文说法：`we can ensure replicas are always in-sync by utilizing a consensus algorithm such as Paxos or Raft`。
   - 正确说法：前半句把共识协议与异步复制延迟混为一谈。Paxos/Raft 实现的是**法定人数复制**，与异步复制是**不同的复制协议**；不能给异步复制的 MySQL 主从「加上 Raft」。消除陈旧读有三条路：全走主库、同步/半同步复制、换基于共识的分布式数据库。（后半句的 YugabyteDB / CockroachDB 是准确的。）

5. **`FAILED` 状态把「明确失败」和「结果未知」混为一谈**
   - 原文说法：枚举为 `NOT_STARTED`、`EXECUTING`、`SUCCESS`、`FAILED`。
   - 正确说法：缺少「未知」状态。`FAILED` 同时表达「卡被拒」（终态）与「超时结果不明」（**非终态**），把后者当 `FAILED` 会提示重试，而钱已扣——**用户重试即被重复扣款**。必须有独立的 `UNKNOWN` / `PENDING_CONFIRMATION` 状态，且**只要结果未知就必须查询，绝不重试扣款**。

### 补充
1. **复式记账的完整原理与工程实现**：为什么不能用简单的余额字段（七个理由）、账本里有哪些账户（尤其易被忽略的 **PSP 清算账户**）、怎么用 SQL 校验借贷平衡。
2. **幂等键的完整设计**：该由谁生成（**必须客户端生成并持久化**）、必须存什么（完整响应、请求哈希、`client_id` 复合主键）、并发竞态处理、过期时间（受客户端重试窗口与 PSP 幂等窗口双重约束，**必须取小值**）。
3. **支付状态机的三条铁律**：终态不可变更、状态只能单向流转、状态转移必须原子校验；另需只追加的状态转移审计表。
4. **重试的抖动、上限、断路器，以及「绝不能重试」的场景**：没有抖动会导致惊群效应；**「已提交但未收到响应」的模糊态绝对不能重试，只能查询**。
5. **「用户看到失败但其实成功了」的完整处理**：五层（界面只显示处理中、前端幂等、webhook 唯一权威、补偿任务兜底、主动通知），以及反向情况的冲正流程。
6. **对账的差异分类与「时间差」陷阱**：长款/短款/金额不符/状态不符/重复；**结算截止时刻在途的交易会被误判为差异，必须排除**。
7. **同步 vs 异步通信的术语精确化**：业界标准术语是**点对点 / 竞争消费者**和**发布-订阅 / 扇出**；Kafka 组内是队列、组间是发布订阅，顺序保证只在分区内、不支持单条消息 ack。
8. **金额不能只用「字符串」就完事**：传输层用字符串正确，但**存储层应用最小货币单位的整数**；且不同货币最小单位不同（USD 2 位、JPY 0 位、KWD 3 位），必须与 `currency` 一起解释。
9. **出账流程的合规与现金流细节**：KYC/AML、制裁名单筛查、税务申报，以及**可用余额 vs 待结算余额**的区分（PSP 打款通常 T+1 到 T+3）。

## 第 27 章：Digital Wallet（数字钱包）

> 原笔记本章整体质量很高（尤其事件溯源与 CQRS 部分），但有几处术语、代码和表述需要修正。

### 勘误
1. **`TC/C` 应写作 `TCC`，且它不是 2PC 的「变体」**
   - 原文说法：使用 `TC/C`，并称它是「2PC 协议的一个变体」。
   - 正确说法：① 业界标准名称是 **TCC（Try-Confirm-Cancel）**；② TCC 第一阶段就**提交了本地事务**，不长期持锁，属于**补偿型事务**族（与 Saga 同族），与 2PC 是**替代关系**而非变体。工业界最有影响力的实现是蚂蚁的 **Apache Seata**。

2. **分片示例代码存在负数取模的隐患**
   - 原文说法：`Int myPartition = accountID.hashCode() % partitionNumber;`
   - 正确说法：Java 的 `%` 对负数返回负结果（`String.hashCode()` 可能为负，如 `"polygenelubricants".hashCode()` 等于 `Integer.MIN_VALUE`），会下标越界或路由错误。应用 `Math.floorMod`。此外 `% partitionNumber` 在分片数变化时几乎全量迁移，生产应改用**一致性哈希**或**预先划分远多于物理节点数的逻辑分片**。

3. **「本地磁盘方案不 durable」的表述不准确**
   - 原文说法：`The previous approach, although performant, wasn't durable.`
   - 正确说法：把**持久性**与**可用性/可靠性**混在一起了。本地磁盘 + mmap + RocksDB 在持久性上是合格的（进程崩溃不丢），它缺的是**冗余**（磁盘坏了数据就没了）。正确说法：短板是**没有副本、存在单点故障**。持久性 ≠ 高可用。

### 补充
1. **三阶段提交（3PC）**：理解「2PC 为什么阻塞」的最好对照；它假设网络不会分区，该假设在真实网络中不成立，工业界基本不用。
2. **TCC 的三种失败模式**：Confirm 失败只能不断重试（故 Confirm 必须幂等）、空回滚（Empty Rollback）、悬挂（Suspension）——TCC 面试高频考点，原笔记只覆盖了第三个的一半。
3. **幂等性的实现方式**：用唯一事务 ID 建去重表，把「插入去重记录」和「执行业务操作」放在同一个本地事务里。
4. **余额不能为负，并发下如何保证**：四种做法按推荐度排列——条件更新（推荐）、乐观锁、悲观锁、数据库约束兜底。条件更新把检查与扣减合并为原子操作，避免 **TOCTOU**。
5. **对账（Reconciliation）与审计**：内部一致性 / 内部账实相符 / 外部对账（T+1）/ 监管报送四层；核心工具是**复式记账**。对账只能**发现**差异，事件溯源才能**定位**根因。
6. **现实参照——100 万 TPS 意味着什么**：真实大型支付系统峰值在每秒几十万笔量级，100 万 TPS 已超过绝大多数真实支付系统峰值；要能区分「设计目标」与「行业常态」。
7. **ZooKeeper 之外的配置存储选择**：今天 **etcd** 和 **Consul** 更常见、更轻量；ZooKeeper 正被逐步替代（Kafka 从 2.8 起支持 KRaft）。

## 第 28 章：Stock Exchange（股票交易所）

> 原笔记本章整体质量高（尤其「关键路径剥离」和「确定性」两节），但有几处事实错误、代码 bug 和概念混淆必须指出。

### 勘误
1. **事件溯源的章节链接是错的**
   - 原文说法：`Event sourcing is discussed in-depth in the [digital wallet chapter](../chapter28)`。
   - 正确说法：数字钱包是第 27 章，应指向 **`../chapter27`**；`chapter28` 指向本章自己，形成自我引用的坏链接。

2. **撮合伪代码存在超卖 bug**
   - 原文说法：`Quantity matched = min(limitIter.next.quantity, order.quantity);`
   - 正确说法：应为 **`leavesQuantity`**（剩余待成交量）。用 `order.quantity` 在多轮撮合时会导致累计成交超过原始数量——例：`quantity=100`，对手方 30 手、80 手，错误代码累计成交 **110 手**（超卖 10 手），正确代码为 100 手。真实系统中超卖意味着凭空创造持仓。

3. **AMM 不是传统交易所的趋势**
   - 原文说法：`modern exchanges rely ... on automatic market makers (AMM) to avoid maintaining an order book`。
   - 正确说法：AMM 是**去中心化金融（DeFi）**概念（用公式定价、不维护订单簿，如 Uniswap 的 `x × y = k`）。传统交易所仍维护订单簿（提供价格发现与透明度），趋势是云基础设施 + **指定做市商 / 流动性提供者计划**（做市商仍在订单簿挂单，只是承担流动性义务）。

4. **订单状态缺少「部分成交」**
   - 原文说法：`status` 为 `new / canceled / filled` 三种。
   - 正确说法：缺少 `PARTIALLY_FILLED`，而原文自己也说限价单可能部分成交。至少需要 **NEW / PARTIALLY_FILLED / FILLED / CANCELED / REJECTED** 五种——客户端和风控都依赖准确状态。

5. **「所有交易所都把一切放在一台服务器上」是过度概括**
   - 原文说法：`typically run everything on one gigantic server`。
   - 正确说法：原文 Wrap Up 自己已承认并非所有交易所都这样。准确表述是**撮合核心（matching core）单节点单线程**（为确定性与微秒级延迟），而**外围服务（网关、行情分发、报送、监控、历史查询）是分布式的**。更精确的说法是「关键路径在同一个故障域内」。

6. **「美国市场有三级报价」的表述不准确**
   - 原文说法：`The US market has three tiers of price quotes - L1, L2, L3`。
   - 正确说法：L1/L2/L3 是**行业通用的行情深度分级约定**（L1 最优买卖价、L2 多档聚合深度、L3 逐笔明细），全球通用，不是美国特有制度。真正属于美国监管的是 **NMS / Reg NMS**（订单保护规则等）。

### 补充
1. **为什么不能用普通数据库做撮合**：磁盘 IO（尤其 `fsync`）、锁竞争、GC 停顿、SQL 解析开销、不可预测的尾延迟；正确做法是**内存撮合 + 顺序写 WAL + 异步写数据库**。
2. **为什么交易所不用 Raft/Paxos 做撮合**：Raft 每笔提交都要等**多数派确认**（几百微秒到毫秒，受最慢节点拖累）；交易所用**主备 + 异步日志复制**（几十微秒），用同机架同步复制 + 定期快照控制风险。**Raft 的正确用法是控制平面（选主），不是数据平面。**
3. **连续竞价、集合竞价与部分成交**：连续竞价（随到随撮）vs 集合竞价（开盘/收盘统一定价、最大化成交量）；`filledQuantity + remainingQuantity = quantity` 是必须永远成立的不变量。
4. **订单簿的有序索引结构**：价格维度用**红黑树 / 跳表**（O(log N)），价格范围固定且 tick 固定时可用**数组按 tick 索引**做到 O(1)；档位内用**双向链表**实现 FIFO，配合 `orderMap` 实现 O(1) 撤单。
5. **行情可以丢包，订单不能——为什么？**：行情是**完整状态快照流**（丢一帧可由下一帧覆盖），订单是**增量事件**（丢了永久缺失）。
6. **公平性与机房托管的矛盾**：等长线缆、统一接入点、速度缓冲（Speed Bump，IEX 的著名机制）——用「故意更慢」换取「更公平」。
7. **延迟指标的量级澄清**：毫秒级指端到端（含网络、网关、风控），微秒级指撮合引擎内部；现代主流交易所撮合内核在微秒级，端到端在几十微秒到亚毫秒级。
