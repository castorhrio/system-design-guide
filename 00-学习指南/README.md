# 学习指南

> 这套笔记怎么用，以及怎么判断自己是不是真的学懂了。

## 一、这套笔记是什么

它是一份**读书笔记的重写版**。原项目 `liquidslr/system-design-notes` 把 Alex Xu《系统设计面试》两卷书的内容压缩成了 28 章速查笔记——很适合复习，但不适合**第一次学**。

原因有三：

1. **它假设你已经懂了。** 原笔记直接说"用一致性哈希解决"，但没解释为什么需要一致性哈希。
2. **它省略了工程细节。** 知道"用 Redis 存计数器"和知道"为什么必须用 Lua 脚本保证原子性"是两件事。
3. **它有错误和过时内容。** 详见[勘误与补充汇总](../99-附录/勘误与补充汇总.md)。

所以这套笔记在保留原文全部信息量的基础上，补上了讲解、勘误和缺失内容。

## 二、每章的结构，以及各节怎么用

每一章都是同一个骨架。熟悉之后，你可以按需跳读。

### 本章导读

**3–6 句话，回答"这章要解决什么问题"。**

建议**必读**。它会告诉你这章在整个体系里的位置，以及学完能回答什么问题。如果你读完后觉得"这章跟我没关系"，可以跳过整章——这是设计意图。

### 你将学到

要点清单。用来自查：读完后能不能把每一条讲给别人听。

### 正文（编号小节）

按原项目结构逐节展开。**这是主体，篇幅最长。**

阅读时注意两种标记：

- **引用块（`>`）** 里通常是我补充的**工程实践、常见误区或勘误提示**。这些是原笔记没有的，往往比正文更有价值。
- **表格** 用来做横向对比（比如五种限流算法的取舍）。**表格是速查入口**，复习时先看表格。

### 勘误与补充

**这是这套笔记最重要的部分。**

- **勘误**：原文哪里说错了、为什么错、正确说法是什么、初学者该知道的延伸背景。
- **补充**：原文完全没讲、但对理解这章很关键的主题。

如果你只有 10 分钟读一章，读这一节 + 面试速记。

### 常见误区

表格形式：`错误理解 → 为什么错 → 正确理解`。

这些是**面试中的减分项**——说出错误理解比不说话更糟。建议通读。

### 面试速记

四个部分：

| 部分 | 用途 |
|---|---|
| 一句话概括 | 面试时被问"介绍下 X"，先用这句定调 |
| 必答要点 | 不提到就是没答完整 |
| 加分项 | 提到能体现深度 |
| 高频追问 | 面试官接下来大概率问什么，附简答 |

### 延伸阅读

原项目的链接 + 我补充的资料。**真想把某章学透，必须读原文资料**——笔记永远替代不了原始论文和官方文档。

## 三、三种读法

### 读法 A：精读（推荐，适合系统学习）

按[学习路线图](学习路线图.md)分阶段推进。每章：

1. 读「本章导读」，确认这章要解决什么问题
2. 读正文，遇到不懂的概念先记下来，继续往下读（很多概念会在后面章节展开）
3. 读「勘误与补充」，修正刚才形成的认知
4. 读「常见误区」，对照自己有没有中招
5. 合上笔记，**用自己的话把这一章讲一遍**（可以对着空气讲，或写下来）

**关键在最后一步。** 看得懂和讲得出是两回事。

### 读法 B：速通（适合面试前突击）

1. 先读[高频面试题速查](../99-附录/高频面试题速查.md)
2. 对不熟悉的章节，只读该章的「勘误与补充」+「面试速记」
3. 面试前一晚，过一遍「常见误区」表格

### 读法 C：查漏（适合已有经验的人）

1. 打开[勘误与补充汇总](../99-附录/勘误与补充汇总.md)
2. 只看第一节「按错误类型速查」的五张表
3. **每一条都问自己："我原来是不是也这么理解的？"** 凡是答"是"的，去读对应章节

这是投入产出比最高的读法——直接检查你认知里的错误，而不是从头学一遍已经会的东西。

## 四、五个常见的学习误区

### 误区 1：把术语背下来就算学会了

"一致性哈希"这四个字谁都会说。真正的问题是：

- 加一个节点，具体有多少 key 需要迁移？
- 节点很少的时候分布会不会不均？不均到什么程度？
- 虚拟节点是解决什么问题的？加多少个合适？
- 它解决不了什么问题？

**判断标准**：你能不能给出具体数字和边界条件。

### 误区 2：只看方案，不看代价

每个技术方案都是**交易**，不是纯粹的进步。

- 缓存 → 换来性能，付出**一致性**和**内存成本**
- 分片 → 换来扩展性，付出**跨片 JOIN 能力**和**运维复杂度**
- 消息队列 → 换来解耦和削峰，付出**最终一致性**和**运维一套中间件**的成本

**面试时只说好处不提代价，是明显的减分项。**

### 误区 3：以为存在"标准答案"

系统设计没有最优解，只有**在给定约束下的合理选择**。

同样设计一个信息流：日活 10 万和日活 1 亿，架构完全不同；能容忍 5 秒延迟和必须 100 毫秒响应，架构也不同。

**永远先问约束**（这也是第 3 章框架的第一步）。

### 误区 4：跳过"无聊"的基础章

第 1 章（扩展）、第 2 章（估算）、第 3 章（框架）看起来最没技术含量，但：

- 后面 27 章都在用第 1 章的组件
- 第 2 章的估算能力直接决定你设计的方案规模对不对
- 第 3 章的框架是你回答任何一道题的**流程**

跳过它们，后面会处处卡壳。

### 误区 5：读完不做题

系统设计是**技能**，不是知识。就像读游泳教材不会让你会游泳。

每读完一个阶段，必须找真题练手，并且**限时、写下来**。写下来才会发现：脑子里想清楚的东西，落到纸上全是漏洞。

## 五、怎么判断自己真的学懂了

用这三个问题自查每一章：

1. **能不能讲给一个没学过的人听？**
   如果必须用术语才能解释清楚，说明你没真懂。比如"缓存击穿就是热点 key 失效"，这句话没有解释任何东西。

2. **能不能说出它解决什么问题、代价是什么？**
   任何只讲好处不讲代价的理解，都是不完整的。

3. **能不能举出一个它不适用的场景？**
   知道边界才算真正掌握。比如"一致性哈希不适合什么场景"——它不适合需要强一致顺序的场景，也不解决热点 key。

三个问题都答得上来，这一章就算过了。

## 七、最后一句

系统设计能力的本质是**在信息不完备的情况下做权衡**。

这套笔记能给你的是"别人已经踩过的坑"和"已经被验证过的模式"。但它给不了你**判断力**——判断力只能来自：自己设计、自己搞砸、自己复盘。

所以，**读完一章就去设计一个东西**。哪怕只是给你现在做的项目画一张架构图，也比读完 28 章不动手强。
