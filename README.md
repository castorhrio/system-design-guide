> 面向初级开发者的系统设计教程 —— 译自并大幅增补自 [liquidslr/system-design-notes](https://github.com/liquidslr/system-design-notes)

这套笔记基于 Alex Xu 的《系统设计面试：内幕指南》（System Design Interview: An Insider's Guide，第 1、2 卷）。

**它不是一份翻译稿，而是一次重构。** 原项目是一份很优秀的英文速查笔记，但它是为"已经懂系统设计的人"准备的复习材料——压缩了大量推导过程，省略了工程细节，还存在术语过时、表述不准确和内容缺失的问题。这套中文版做了四件事：

| | 做了什么 | 结果 |
|---|---|---|
| **一、完整翻译** | 保留原项目全部 28 章的信息量，术语一律中英对照 | 查英文一手资料时不会对不上号 |
| **二、教学重构** | 每章增加导读、循序渐进讲解、常见误区、面试速记 | 不需要先懂系统设计才能读懂 |
| **三、勘误修正** | 逐条指出原文的错误、过时表述 | **127 条勘误**，集中在[附录](99-附录/勘误与补充汇总.md) |
| **四、补充扩展** | 补齐原笔记缺失的工程细节与现代实践 | **182 条补充**，含大量原文完全没有的主题 |

**规模**：28 章 · 91.5 万字 · 392 张图

## 每章的结构

每一章都是同一个骨架，你熟悉之后可以直接跳到需要的部分：

```
# 第 N 章：标题
├── 本章导读          这章解决什么问题、为什么重要（3-6 句）
├── 你将学到          要点清单
├── 正文（编号小节）    按原项目结构逐节讲解，配图
├── 勘误与补充         ← 这套笔记的核心价值
│   ├── 勘误 N        原文哪里错了 / 为什么错 / 正确说法 / 延伸
│   └── 补充 N        原文缺失的主题，完整讲清楚
├── 常见误区          表格：错误理解 → 为什么错 → 正确理解
├── 面试速记          一句话概括 / 必答要点 / 加分项 / 高频追问
└── 延伸阅读          原项目链接 + 补充资料
```

**如果你时间紧张**，只读「勘误与补充」和「面试速记」两节，收益最高。

## 原笔记里最值得注意的几类问题

完整清单见[勘误与补充汇总](99-附录/勘误与补充汇总.md)，这里挑几个典型的：

**术语过时**

- 通篇使用 `Master-Slave`（主/奴）—— 业界已弃用，正确说法是 `Primary-Replica`（主副本）或 `Leader-Follower`
- `Leaking Bucket` → 正确术语是 `Leaky Bucket`（漏桶）
- `TC/C` → 正确写法是 `TCC`（Try-Confirm-Cancel）

**技术事实错误**

- "消息队列是持久化组件，**存在内存中**" —— 这两句自相矛盾，且后半句是错的。消息队列必须落盘，否则 Broker 重启就丢消息
- "CAP 三选二" —— P（网络分区）是物理事实，不是可选项。现实只有 CP 和 AP，CA 系统不存在
- "布隆过滤器解决哈希冲突" —— 布隆过滤器只能做前置过滤，冲突裁决必须靠唯一索引
- "`ORDER BY score DESC` 慢是因为全表扫描" —— 有索引时 Top-K 是 O(log N + 10)，真正的瓶颈是排名查询

**数字过时**

- 延迟数字表标注 2020 年，实际是 Jeff Dean 2010 年前后的数据（SSD 随机读已从 150 µs 降到 20–100 µs）
- "推文上限 140 字节" —— 2017 年已放宽到 280 字符，且字符数不等于字节数
- YouTube 的日观看量、上传量、广告收入均为 2020 年数据

**内容缺失**（182 条补充中的代表）

- 缓存三大故障（穿透 / 击穿 / 雪崩）的区别，以及 Cache-Aside / Write-Through / Write-Back 三种读写模式
- Kafka 的 KRaft 演进（ZooKeeper 已在 4.0 被彻底移除）
- 邮件送达率的核心：SPF / DKIM / **DMARC** 三件套
- 对象存储的预签名 URL、分片上传、ETag 陷阱
- 支付系统的复式记账原理与对账机制
- TCC 的三种失败模式（空回滚、悬挂、Confirm 失败）

## 关于这套笔记

**读者定位**：会写业务代码、但没做过系统设计的开发者。不需要你事先懂分布式，但需要你能读代码。

**写作原则**：

1. **先讲问题，再讲方案** —— 不会上来就说"用一致性哈希"，而是先问"加一台机器为什么 90% 缓存会失效"
2. **解释"为什么"，不只说"是什么"** —— 每个选型都讲清解决了什么痛点、代价是什么
3. **诚实** —— 原文对的地方就说是对的，不确定的数字宁可标注"量级参考"也不编造

## 动手建议

读系统设计最容易犯的错是"看懂了，但没真懂"。每学完一章，建议做一件事：

- **第 1–3 章**：用纸笔画出你公司/你熟悉的一个系统的架构图，标注每个组件的作用
- **第 4–7 章**：本地起一个 Redis，用 `INCR` + `EXPIRE` 手写一个限流器
- **第 8–15 章**：挑一道题，在 45 分钟内完整走一遍第 3 章的四步框架，写下来
- **第 16–28 章**：找对应的开源项目读源码（Kafka、MinIO、HBase、Redis）

各章的「延伸阅读」里给了具体资料。

## 本地重建阅读站

上面的在线阅读站就是本仓库的 Markdown 编译出来的，编译脚本在 `tools/build_site.py`：

```bash
pip install markdown-it-py linkify-it-py
python tools/build_site.py        # 产物在 .site/（已加入 .gitignore）
```

脚本会渲染全部 35 个 Markdown、生成侧边目录、本页目录、上下页导航和全文搜索索引，
输出纯静态 HTML（不需要 Jekyll）。把 `.site/` 的内容推到 `gh-pages` 分支即可更新线上站点。

修改任何一章后重新执行一次，线上内容就会跟着更新。
