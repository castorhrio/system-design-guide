这份表怎么用

这份术语表是给你边读边查用的，不是拿来背的。遇到正文里一个眼熟但说不清的词，回到这里看一眼"它是干什么用的"，然后回去继续读。

为什么一定要中英对照？ 因为中文资料和英文原文常常不是一套词：

  • 同一个概念，不同中文译法并存。比如 Sharding 有人叫"分片"，有人叫"分区"；Cache-Aside 有人叫"旁路缓存"，有人叫"旁路模式"，还有人直接叫"懒加载"。你只记住中文名，搜索时会漏掉一大半资料。
  • 同一个中文词，可能对应完全不同的英文。比如"一致性"在 CAP 里是 Consistency，在 ACID 里也是 Consistency，但两者说的根本不是一回事；"分区"在数据库里是 Sharding，在网络里是 Network Partition。
  • 一手资料几乎都是英文。Kafka 官方文档、Raft 论文、AWS 白皮书、Prometheus 文档——想深挖任何一块，都得用英文名去搜。

所以本表的用法是：先用中文名定位，再用英文名去搜原文。

几点说明：

  • 每个术语给的是"它是干什么用的"，不是同义词翻译。看不懂解释时，去对应章节看完整上下文。
  • 分组只是方便查找，很多术语跨组。比如 Quorum 既在"存储与数据库"里出现，也在"分布式协调"里出现。
  • 表格里放不下的易混淆术语，会单独用引用块展开对比，这些往往是面试里最容易被追问的点，建议重点看。

1. 基础与架构

冗余 Redundancy 故意保留多余副本，让单个部件坏掉不影响整体。
幂等性 Idempotency 同一个操作执行多次和执行一次的结果相同，是重试安全的前提。

解耦 Decoupling 让组件之间不直接依赖，可各自独立演进和伸缩。
可扩展性 Scalability 系统在负载增长时通过加资源维持性能的能力。
可用性 Availability 系统在需要时能正常提供服务的时间比例。
可靠性 Reliability 系统长时间不出错、不出故障的概率。
容错 Fault Tolerance 部分组件故障时系统仍能继续工作。
服务水平协议 SLA（Service Level Agreement） 对客户承诺的服务指标（如 99.9% 可用），违约要赔偿。
服务水平目标 SLO（Service Level Objective） 团队内部设定的目标值，通常比 SLA 更严。
服务水平指标 SLI（Service Level Indicator） 实际测量出来的指标，用来判断是否达成 SLO。
错误预算 Error Budget 允许的不可用额度，用完就冻结变更、先修稳定性。

分位 Percentile（P95 / P99 / P999） 表示"有百分之多少的请求比这个值更快"。
读写比 Read/Write Ratio 读请求与写请求的比例，决定系统该往哪一边优化。
日活 / 月活 DAU / MAU 日活跃用户数与月活跃用户数，是规模估算的起点。
功能需求 Functional Requirements 系统"要做什么"。
非功能需求 Non-Functional Requirements 系统"要做到多好"，如延迟、可用性、规模。

降级 Fallback 主路径不可用时返回一个可接受的替代结果。
回滚 Rollback 出问题时把变更退回到之前的状态。

易混淆：限流算法的四种写法

固定窗口计数器（Fixed Window Counter）：把时间切成固定的分钟/秒格子计数。实现最简单，但格子边界会放过两倍流量。 滑动窗口日志（Sliding Window Log）：记录每个请求的时间戳，精确但内存开销大。 滑动窗口计数器（Sliding Window Counter）：用"上一格 + 当前格"按比例加权估算，是精度和开销的折中。 令牌桶（Token Bucket）：以固定速率往桶里放令牌，请求要拿令牌才能过。允许突发，是业界最常用的方案。 漏桶（Leaky Bucket）：请求先入队，再以恒定速率流出。不允许突发，输出绝对平滑。

一句话记法：令牌桶管"平均速率 + 允许突发"，漏桶管"输出绝对匀速"。

易混淆：本地限流 vs 全局限流

本地限流（Local Rate Limit）：每台服务器各自计数。实现简单，但 N 台机器实际总配额是 N 倍，配额不准。 全局限流（Global Rate Limit）：把计数集中到 Redis 等共享存储。配额准确，但每次请求都要访问共享存储，多了一次网络往返，且共享存储本身可能成为瓶颈。

工程上的常见做法是分层：本地限流挡住绝大部分突发，全局限流做最终兜底。

易混淆：写扩散 vs 读扩散

写扩散 / 推（Fan-out on Write）：用户发一条内容时，立刻把它写进所有粉丝的收件箱。读的时候直接读自己的收件箱，读很快，写很贵。 读扩散 / 拉（Fan-out on Read）：发内容时只写一份，读的时候再去拉所有关注对象的内容合并。写很便宜，读很贵。

大 V 问题是分水岭：一个有几千万粉丝的明星发一条动态，写扩散要写几千万次，系统直接被打爆。所以真实系统常用混合策略——普通用户走写扩散保证读体验，大 V 走读扩散避免写风暴，读取时再把两路结果合并。

B+ 树 B+ Tree 关系型数据库默认的磁盘索引结构，读性能稳定。
聚簇索引 Clustered Index 索引顺序就是数据的物理存储顺序。
跳表 Skip List 用多级链表实现有序查找，Redis 有序集合用它。

反熵 Anti-Entropy 后台比对副本差异并修复，保证最终一致。
物化视图 Materialized View 把查询结果预先算好存起来，读得快但写要维护。
星型模型 Star Schema 数据仓库里"事实表 + 维度表"的组织方式。
事实表 Fact Table 存度量值（如点击次数、金额）的表。
范式化 Normalization 消除冗余、把数据拆成多张表。
反范式 De-normalization 故意冗余以换取读取性能。
唯一约束 Unique Constraint 数据库层保证某字段不重复，是防重的前置防线。
UPSERT UPSERT 存在就更新、不存在就插入的原子操作。
原子条件更新 Atomic Conditional Update 带条件的原子写，常用来实现乐观锁。
乐观锁 Optimistic Locking 先读版本号，写入时校验版本没变，冲突就重试。
悲观锁 Pessimistic Locking 先加锁再操作，简单但并发度低。
死锁 Deadlock 两个事务互相等待对方持有的锁，永远解不开。
写放大 Write Amplification 一次逻辑写实际引发多次物理写，是 SSD 寿命和性能的敌人。
生命周期策略 Lifecycle Policy 按规则把老数据从热存储自动迁移到冷存储或删除。
冷存储 Cold Storage 访问极少、成本极低的存储层，取回很慢。
对象存储 Object Storage 以对象为单位、通过 HTTP 访问的存储，适合海量非结构化数据。
块存储 Block Storage 提供裸磁盘块，由上层文件系统自己管理。
文件存储 File Storage 提供目录树和文件语义的网络存储。
对象不可变 Object Immutability 对象写入后不能原地修改，只能整体替换。
多段上传 Multipart Upload 把大对象切成多段并行上传，失败只重传某一段。
断点续传 Resumable Upload 记录上传进度，网络中断后可以继续。
预签名 URL Presigned URL 临时授权的下载 / 上传链接，客户端直连存储而不经过应用服务器。
内容寻址存储 Content-Addressable Storage 用内容哈希作为地址，天然去重且可校验。
数据路由服务 Data Routing Service 根据 key 把请求路由到正确的数据节点。
放置服务 Placement Service 决定副本放在哪些节点，并维持整体均衡。

易混淆：耐久性 vs 可用性

耐久性（Durability）：数据不丢。对象存储常喊"11 个 9"，指的是存进去的数据几乎不可能永久丢失。 可用性（Availability）：服务能用。通常"4 个 9"，指的是请求能得到响应的时间比例。

两者互不保证。一个系统可以数据永不丢失但整整一天无法访问（可用性差、耐久性好），也可以随时能读写但偶尔丢数据（可用性好、耐久性差）。对象存储的答案通常是：用纠删码 + 多副本把耐久性做到极致，用多机房冗余把可用性做到四个九。

易混淆：四种存储语义

Cache-Aside（旁路缓存）：应用自己管缓存，读时先查缓存、未命中再查库并回填。最常用。 Read-Through（读穿透）：缓存组件自己负责回源，应用只和缓存打交道。 Write-Through（写穿透）：写的时候同步写缓存和数据库，缓存永远和库一致，但写变慢。 Write-Back（写回）：只写缓存，之后异步刷回数据库，写最快，但宕机会丢数据。

记忆要点：穿透是同步（安全但慢），写回是异步（快但可能丢）。

3. 缓存

中文名 英文名 一句话解释
缓存 Cache 把慢存储里的热点数据放到快存储，用空间换时间。
缓存命中 / 未命中 Cache Hit / Miss 请求在缓存里找到 / 没找到数据。
缓存命中率 Hit Rate 命中次数占总请求的比例，直接决定缓存的价值。
旁路缓存 Cache-Aside 应用自己管缓存：读时先查缓存，未命中再查库并回填。最常用。
读穿透 Read-Through 缓存组件自己负责回源，应用只和缓存打交道。
写穿透 Write-Through 写时同步更新缓存和数据库，一致性最好但写变慢。
写回 Write-Back 只写缓存，之后异步刷回数据库，写最快但宕机可能丢数据。
写旁路 Write-Around 写的时候绕过缓存直接写库，避免写了却不会被读的数据污染缓存。
缓存失效 Invalidation 数据变了之后让旧缓存不再被使用。
过期时间 TTL（Time To Live） 给缓存设一个存活时长，到期自动失效。
淘汰策略 Eviction Policy 缓存满了之后决定先踢掉谁的规则。
最近最少使用 LRU（Least Recently Used） 踢掉最久没被访问的那个，适合有明显时间局部性的场景。
最不经常使用 LFU（Least Frequently Used） 踢掉访问次数最少的那个，适合长期热点，但对新数据不友好。
先进先出 FIFO（First In First Out） 按进入顺序淘汰，最简单但完全不管访问频率。
缓存穿透 Cache Penetration 查一个根本不存在的数据，缓存和数据库都没命中，请求每次都打到数据库。
缓存击穿 Cache Breakdown 某个热点 key 突然过期，瞬间大量请求同时打到数据库。
缓存雪崩 Cache Avalanche 大批 key 同时过期，或者缓存集群整体宕机，数据库被瞬间压垮。
惊群 Thundering Herd 大量请求同时发现缓存失效，一起冲向后端。
空值缓存 Null Caching 把"查不到"也缓存起来（短 TTL），用于防穿透。
布隆过滤器预检 Bloom Filter Pre-check 查询前先用布隆过滤器挡掉肯定不存在的 key，用于防穿透。
缓存预热 Cache Warming 上线或扩容后提前把热点数据加载进缓存，避免冷启动被打穿。
缓存一致性 Cache-DB Consistency 让缓存和数据库的数据保持一致的策略总称。
延迟双删 Delayed Double Delete 更新库后先删缓存，隔一小段时间再删一次，兜住并发读到旧值的窗口。
双写 Double Write 同时写缓存和数据库，简单但容易不一致。
计数器缓存 Counter Cache 把点赞数、阅读数这类高频计数放缓存里累加。
内容缓存 Content Cache 缓存静态内容（图片、HTML），通常放在 CDN 层。
单飞 Singleflight 同一个 key 的并发未命中只放一个请求去回源，其余等待复用结果。
多级缓存 Multi-level Cache 本地缓存 + 分布式缓存分层，兼顾速度和容量。
一致性哈希环 Consistent Hash Ring 缓存节点按哈希环分布，加减节点时只影响相邻区间。

易混淆：缓存穿透 vs 击穿 vs 雪崩（必看）

三个词都描述"请求绕过缓存打到数据库"，但触发原因和范围完全不同：

触发原因 范围 典型解法
穿透（Penetration） 查的数据压根不存在 单个（或一批伪造的）不存在的 key 空值缓存、布隆过滤器、参数校验
击穿（Breakdown） 单个热点 key 恰好过期 单个热点 key 互斥锁重建、逻辑过期、热点永不过期
雪崩（Avalanche） 大批 key 同时过期，或缓存整体故障 全库 / 全集群 过期时间加随机抖动、多级缓存、熔断降级

一句话区分：穿透是"数据不存在"，击穿是"一个热点过期"，雪崩是"一批同时过期或缓存整个挂了"。 另外注意击穿和惊群（Thundering Herd）常被混用：击穿强调"热点 key 失效"这个原因，惊群强调"大量请求同时冲向后端"这个现象，二者经常同时出现。

易混淆：LRU vs LFU

LRU（最近最少使用）：看"多久没被访问"。刚被访问过的数据排在最前，淘汰队尾。 LFU（最不经常使用）：看"总共被访问了多少次"。累计次数少的先淘汰。

差别在"突发的旧数据"上：LRU 会把一个刚刚被扫过一次的冷数据放到队首，把真正的热点挤出去（缓存污染）；LFU 则不会，但新加入的热数据因为次数少，很容易被误杀（需要额外的计数衰减或新数据保护机制）。 工程上常把两者结合，例如 Redis 的近似 LRU，以及各类"LRU + 频率"的混合策略。

4. 一致性理论

中文名 英文名 一句话解释
CAP 定理 CAP Theorem 网络分区发生时，一致性和可用性只能二选一。
PACELC PACELC CAP 的补充：没分区时（E），还要在延迟（L）和一致性（C）之间权衡。
分区容错 Partition Tolerance 网络分区（节点间通信中断）时系统仍能继续运行。
一致性（CAP 中的） Consistency 所有节点在同一时刻看到相同的数据。
可用性（CAP 中的） Availability 每个请求都能在有限时间内得到非错误响应。
强一致性 Strong Consistency 写入成功后，任何后续读取都能看到这次写入。
弱一致性 Weak Consistency 写入后不保证何时能被读到。

原子性 Atomicity 事务里的操作要么全做，要么全不做。
一致性（ACID 中的） Consistency 事务前后数据都满足业务约束（和 CAP 的 C 不是一回事）。

持久性 Durability 事务提交后，即使宕机数据也不会丢。
隔离级别 Isolation Level 在并发正确性和性能之间选择的档位。

向量时钟 Vector Clock 版本向量的经典实现，用于检测并发写冲突。

易混淆：强一致 vs 线性一致 vs 最终一致

  • 最终一致（Eventual Consistency）：最弱。"现在可能读到旧的，但迟早会一致"。适合点赞数、粉丝数这类可以短暂不准的数据。
  • 强一致（Strong Consistency）：写入成功后立刻能读到新值。但"立刻"的定义可以很模糊。
  • 线性一致（Linearizability）：最强，也是最严格的定义。要求整个系统表现得像只有一份数据，并且操作顺序和真实物理时间一致。任何读到"还没发生的写"或"已经过去的旧值"都算违反。

关系是：线性一致 ⊂ 强一致 ⊂ 最终一致（越往后越宽松）。面试里说"我们要强一致"通常太笼统，能说清"要线性一致还是只要读己之写"才是加分项。

易混淆：ACID 的 C vs CAP 的 C

两个 C 长得一样，含义完全不同：

  • ACID 的 Consistency：指业务约束不被破坏。比如转账前后总金额不变。这是应用层的语义，数据库只是保证事务不会把它搞坏。
  • CAP 的 Consistency：指多个副本看到同一份数据。这是分布式系统层面的语义。

看到 "C" 先问一句：这是在讲事务，还是在讲多副本？

易混淆：2PC / 3PC / TCC / Saga

这四个都是"跨多个服务 / 分片完成一件事"的方案，区别在一致性强度和可用性代价：

方案 思路 一致性 主要问题
2PC（两阶段提交） 协调者先让所有参与者"准备"，全票通过再"提交" 强一致 同步阻塞、协调者单点、参与者长时间持锁
3PC（三阶段提交） 在 2PC 前加一个"CanCommit"预询问 稍弱，减少阻塞 仍然解决不了网络分区下的不一致，实际很少用
TCC（Try-Confirm-Cancel） 业务层面预留资源（Try），再确认（Confirm）或取消（Cancel） 最终一致 需要为每个操作写三个接口，业务侵入大
Saga 把长事务拆成一串本地事务，失败就反向执行补偿操作 最终一致 没有隔离性，中间状态对外可见，补偿逻辑难写

一句话选择：要强一致且能接受阻塞 → 2PC；要高可用、能接受最终一致 → TCC 或 Saga。3PC 基本只出现在教材里。 另外 TCC 里有三个经典坑要特别小心：空回滚（Try 没执行但收到 Cancel）、悬挂（Cancel 先到，Try 后到）、幂等（Confirm / Cancel 被重复调用）。

易混淆：at-most-once / at-least-once / exactly-once

三者描述的是消息在"生产者 → broker → 消费者"整条链路上被处理的次数：

  • 至多一次（At-Most-Once）：先标记已读，再处理。可能丢消息，但绝不重复。适合日志采集这类丢了也不心疼的场景。
  • 至少一次（At-Least-Once）：先处理，成功后再确认。绝不丢，但可能重复。绝大多数消息队列的默认语义，代价是消费端必须自己处理重复。
  • 恰好一次（Exactly-Once）：听起来最理想，但跨网络无法真正实现——因为确认消息本身可能丢失，发送方永远无法区分"对方没收到"和"对方收到了但确认丢了"（这正是两将军问题）。

工程上的"恰好一次"其实是两件事拼出来的：至少一次投递 + 消费端幂等，也就是常说的有效一次（Effectively-once）。 面试里的正确说法是："跨网络的严格恰好一次做不到，我们做的是至少一次加幂等去重，效果上等价于恰好一次。" 直接说"我们用 exactly-once 保证不重复"会被追问到底。

易混淆：事件时间 vs 处理时间

  • 事件时间（Event Time）：这条数据在现实世界发生的时刻，比如用户点击按钮的那一秒。由数据自己带着。
  • 处理时间（Processing Time）：系统处理到这条数据的时刻。由机器时钟决定。

为什么必须区分？因为网络延迟和重试会让两者错开很远。用处理时间做"每分钟点击量"，会把延迟到达的数据算到错误的分钟里，结果完全失真。

代价是：用事件时间就必须处理乱序和迟到——这就是**水位线（Watermark）和允许迟到（Allowed Lateness）**存在的原因。水位线是"我认为某时刻之前的数据都到齐了"的进度信号，它决定了窗口什么时候可以安全输出结果。

易混淆：推 vs 拉

  • 推（Push）：broker 主动把消息送给消费者。延迟低，但 broker 必须知道消费者的处理能力，否则容易把慢消费者压垮。
  • 拉（Pull）：消费者主动来取。消费者自己控制节奏，天然支持批量和回溯，代价是没数据时会空轮询浪费资源。

解决空轮询的办法是长轮询（Long Polling）：没数据时请求先挂起，有数据或超时才返回。Kafka 消费者用的就是长轮询。

易混淆：RED vs USE

两套方法解决的对象不同：

  • RED（Rate / Errors / Duration） 面向请求 / 服务：每秒多少请求、多少失败、耗时多少。适合监控 API、微服务。

易混淆：GeoHash vs 瓦片索引

两者都能把二维空间压成一维，但用途完全不同：

易混淆：复式记账 vs 单纯改余额

初学者最容易写出的支付逻辑是"用户余额减 100，商户余额加 100"。这有两个致命问题：中间任何一步失败，钱就凭空消失或凭空产生；而且没有任何记录能证明账目对不对。

复式记账的做法是：每笔交易同时产生一条借方和一条贷方分录，所有分录的借贷总额永远相等。这样任何时刻都能做一次全局校验——如果借贷不平衡，就一定出了问题。

一句话记法：改余额只记录"结果"，复式记账记录"因果"，并且自带对账能力。

垃圾邮件陷阱 Spam Trap 故意放置的邮箱地址，谁发信给它就说明在乱发垃圾邮件。
退信 Bounce 邮件无法投递时的回执，用于清理无效地址。
贝叶斯过滤 Bayesian Filtering 用统计模型判断邮件是垃圾邮件的概率。
钓鱼 Phishing 伪装成可信方骗取账号密码或资金。
分布式拒绝服务 DDoS 用海量流量把服务打瘫。
速率检查 Velocity Checks 检查短时间内同一用户 / 卡 / IP 的操作频率是否异常。

12. 算法与数据结构

中文名 英文名 一句话解释
哈希函数 Hash Function 把任意输入映射成固定长度摘要，要求分布均匀且不可逆。
哈希表 Hash Table 用哈希值定位数据的键值结构，平均 O(1) 查找。
哈希碰撞 Collision 两个不同输入得到同一个哈希值。
一致性哈希 Consistent Hashing 把节点和数据都放到哈希环上，加减节点时只迁移相邻区间，避免全量重分布。
虚拟节点 Virtual Nodes 给每个物理节点在环上放多个副本位置，让数据分布更均匀。
最小化重分布 Minimized Redistribution 增删节点时只搬动必要的数据，是一致性哈希的核心收益。
最高随机权重 HRW（Rendezvous Hashing） 每个 key 选哈希权重最高的节点，无需维护环结构。
跳转一致性哈希 Jump Consistent Hash 用极小的内存和极快的计算实现均匀分布，但只支持编号节点。
布隆过滤器 Bloom Filter 用位数组判断"一定不存在 / 可能存在"，有假阳性但无假阴性。
计数布隆过滤器 Counting Bloom Filter 支持删除元素的布隆过滤器变体。
计数最小草图 Count-Min Sketch 用固定内存估算元素出现频次，常用于找热点。
超对数 HyperLogLog 用极小内存估算去重后的基数，误差约 2%。
前缀树 Trie 按字符逐层组织的树，天然支持前缀匹配和自动补全。
压缩前缀树 Radix Tree 把只有一个子节点的路径压缩，节省 Trie 的空间。
双数组 Trie Double-Array Trie 用两个数组表示 Trie，查询快、内存省，常用于词典。
有限状态转换器 FST（Finite State Transducer） 更紧凑的前缀结构，Lucene 用它存词典。
有序集合 Sorted Set 每个元素带一个分数、按分数排序的集合，排行榜的基础。
跳表 Skip List 多级索引的链表，实现简单且支持范围查询。
红黑树 Red-Black Tree 自平衡二叉搜索树，保证最坏情况也是 O(log n)。
二叉堆 Heap 能快速取到最大 / 最小元素的结构，用于优先队列。
环形缓冲 Ring Buffer 首尾相接的固定大小缓冲区，读写无锁且不分配内存。
双向链表 Doubly Linked List 每个节点同时指向前后，LRU 靠它实现 O(1) 移动。
位图 Bitmap 用一个 bit 表示一个状态，极度节省内存。
莫顿码 Morton Code 把二维坐标交错编码成一个整数，保留空间局部性。
SimHash SimHash 把文档压成一个指纹，相似文档的指纹汉明距离小，用于查重。
MinHash MinHash 用多个哈希的最小值估计两个集合的相似度。
感知哈希 Perceptual Hashing 对图片内容而非字节做哈希，用于识别近似图片。
TF-IDF TF-IDF 用词频和逆文档频率衡量一个词对文档的重要程度。
BM25 BM25 比 TF-IDF 更成熟的检索相关性打分函数。
芬威克树 Fenwick Tree 支持前缀和查询与单点更新的高效结构，用于排名统计。
广度优先搜索 BFS 逐层扩展的图遍历，用于求无权图最短路径。
Dijkstra 算法 Dijkstra 求带权图单源最短路径的经典算法。
Base62 编码 Base 62 Conversion 用 0-9、a-z、A-Z 表示数字，用于生成短链接。
雪花 ID Snowflake ID 由时间戳 + 机器 ID + 序列号拼成的趋势递增唯一 ID。
通用唯一标识符 UUID 128 位随机 / 结构化 ID，全球唯一但无序。
字典序可排序唯一 ID ULID 兼顾随机性和时间有序性的 ID 方案。
生日悖论 Birthday Paradox 随机取值时，出现碰撞所需的数量远小于取值范围，是 ID 长度设计的依据。
