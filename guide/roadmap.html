学习路线图

28 章按什么顺序读、每阶段花多久、学完要产出什么。

总体安排

四个阶段，难度递进。每个阶段都有明确的产出物——不是"读完"，而是"做出某个东西"。

阶段 章节 目标 产出物
一、打地基 第 1–3 章 建立全局观，掌握答题流程 一张自己画的架构图 + 一次完整的估算
二、攒零件 第 4–7 章 掌握四个核心组件 一个手写的限流器
三、练套路 第 8–15 章 用框架解完整题目 两道限时完成的设计题
四、啃硬骨头 第 16–28 章 理解专业领域系统 一个开源项目的源码阅读笔记

不建议跳阶段。第三部分的题之所以能"练"，是因为第二部分给了你零件、第一部分给了你流程。

阶段一：打地基（第 1–3 章）

目标

建立"一个系统是怎么从一台机器长成分布式系统"的完整图景，并掌握回答设计题的固定流程。

第 1 章　从零到百万用户

这是全书最重要的一章。 后面 27 章反复用到的组件（负载均衡、缓存、CDN、消息队列、分片）都在这里第一次登场。

读的时候注意：

  • 把"用户规模 → 架构变化"的演进表记住（第 13 节），这是一条主线
  • 重点看三个"坑"：主从延迟、缓存三大故障、分片键选择

读完必须能做：画出从用户到数据库的完整请求链路，并说出每个组件解决什么问题。

第 2 章　粗略估算

目标：能在 5 分钟内，从"日活 1 亿"推导出 QPS、存储量、带宽。

读的时候注意：

  • 不要背数字，要记住量级和换算（1 天 ≈ 10^5 秒是最常用的）
  • 原文的延迟数字表已过时，笔记里给了更新版本
  • 关键技巧是"先写假设，再算，最后取整"——面试官看的是推导过程，不是精确结果

读完必须能做：给定"设计一个类似 Twitter 的系统"，5 分钟内算出读写 QPS、5 年存储需求。

第 3 章　系统设计框架

目标：拿到任何一道题，知道第一步做什么、第二步做什么。

四步框架：

1. 理解问题，确定范围    ← 最容易被跳过，也最容易失分
2. 高层设计，取得认同
3. 深入设计
4. 收口总结

读的时候注意：

  • 时间分配（45 分钟面试怎么切）
  • 功能性需求 vs 非功能性需求的区别（笔记里补的，原笔记没有）
  • 每一步的产出物是什么

读完必须能做：拿到一道陌生的题，不看答案，完整走一遍四步，并把过程写下来。

阶段一产出物

  1. 画出你现在负责的（或熟悉的）系统的架构图，标注每个组件的作用
  2. 对那个系统做一次量级估算，看你的估算和实际差多少
  3. 用四步框架口头讲一遍"设计一个短链系统"（不用管讲得好不好，先走完流程）

如果这三件事做不出来，不要进入阶段二。

阶段二：攒零件（第 4–7 章）

目标

掌握四个会被反复使用的核心组件。学完之后，你手里就有"工具"了。

第 4 章　限流器

核心：五种限流算法的取舍。

算法 一句话
令牌桶 匀速放令牌，允许突发
漏桶 匀速流出，不允许突发
固定窗口计数 最简单，但窗口边界会翻倍
滑动窗口日志 精确，但内存开销大
滑动窗口计数 折中方案，近似

重点：分布式限流的原子性问题（为什么必须用 Lua 脚本）、fail-open vs fail-closed。

第 5 章　一致性哈希

核心：为什么 hash(key) % N 在 N 变化时会雪崩，一致性哈希怎么把影响范围降到 1/N，虚拟节点怎么解决分布不均。

重点：这一章非常容易被"背下来"，但要真正理解必须能回答：加一个节点，具体有多少 key 要迁移？节点少的时候分布有多不均？

第 6 章　键值存储

核心：CAP、Quorum、Merkle 树、向量时钟。

这是阶段二最难的章。CAP 的"三选二"说法是错的（笔记里有详细勘误），要理解 P 是物理事实而非选项。

第 7 章　分布式唯一 ID

核心：Snowflake 的位分配、时钟回拨问题、以及为什么随机 UUID 会拖慢数据库。

阶段二产出物

手写一个限流器，本地跑起来：

  1. 用 Redis 的 INCR + EXPIRE 实现固定窗口限流
  2. 用 Lua 脚本把它改成原子操作
  3. 用 ab 或 wrk 压测，验证限流真的生效了
  4. 想清楚：如果 Redis 挂了，你的限流器应该放行还是拒绝？

阶段三：练套路（第 8–15 章）

目标

用前两个阶段学的东西，完整解决八道经典题。

这一阶段的重点不是"学新知识"，而是"练流程"。 每道题都应该按第 3 章的四步框架来走。

八道题的分组

组别 章节 共同点
存储与计算 8. URL 短链、13. 搜索补全 核心是"如何快速查找"，考验数据结构选择
内容分发 14. YouTube、15. Google Drive 核心是"大文件怎么传、怎么存、怎么同步"
实时交互 12. 聊天、10. 通知 核心是"推送通道"和"可靠投递"
内容聚合 11. 信息流、9. 爬虫 核心是"扇出（fan-out）"的代价

建议按组读，同一组内的题对比着看，会发现很多设计手法是共通的。

每道题都要问自己的三个问题

  1. 这道题的核心难点是什么？ （比如短链的核心是哈希碰撞，信息流的核心是扇出）
  2. 推模式还是拉模式？ （很多题都会遇到这个选择）
  3. 规模再涨 10 倍，哪里会先崩？

阶段三产出物

限时完成两道题，写在纸上或文档里，45 分钟一道。

推荐组合：

  • 一道"存储型"：URL 短链（相对简单，适合练手）
  • 一道"扇出型"：信息流系统（涉及推拉权衡，比较有深度）

写完对照笔记检查：你有没有漏掉非功能性需求？有没有算容量？有没有讲代价？

阶段四：啃硬骨头（第 16–28 章）

目标

理解专业领域的系统。这一阶段的 13 章，每一章都涉及一个领域的专门知识。

按主题分组

主题 章节 需要额外补的知识
地理与位置 16、17、18 GeoHash、四叉树、地图投影、路线规划算法
数据管道 19、20、21 消息队列语义、流处理时间语义、可观测性
业务系统 22、23、24 并发控制、邮件协议、对象存储
交易系统 25、26、27、28 分布式事务、幂等、事件溯源、撮合

交易系统那四章是全书难度最高的，也是工程严谨性要求最高的。建议最后读，并且读慢一点。

第 26 章特别说明

支付系统这一章请逐字读。它讲的不是"怎么设计一个支付系统"，而是"在钱的问题上，工程师必须遵守哪些纪律"：

  • 为什么不能只改余额字段，必须用复式记账
  • 为什么"恰好一次投递"不可能实现，正确的目标是什么
  • 为什么有些失败绝对不能重试
  • 为什么对账是必须的（假设系统一定会有错）

这些原则在其他系统里同样适用，只是代价没这么高。

阶段四产出物

挑一个开源项目读源码，写一份阅读笔记。

推荐（按难度递增）：

项目 语言 读什么
MinIO Go 对象存储的分片上传与纠删码
Redis C Sorted Set 的跳表实现（对应第 25 章）
Kafka Java 分段日志、稀疏索引、副本同步（对应第 19 章）
Flink Java 水位线与窗口机制（对应第 21 章）

阅读笔记要写清楚：它用什么数据结构解决了什么问题、为什么不用更简单的方案。

时间投入参考

以下只是相对比例，不是硬性要求。按每天 1–2 小时估算：

阶段 章节数 相对投入 说明
一、打地基 3 20% 第 1 章要反复读
二、攒零件 4 20% 第 6 章最耗时
三、练套路 8 25% 主要时间花在"自己写一遍"
四、啃硬骨头 13 35% 篇幅大、难度高，值得慢读

注意：第四阶段的 13 章占了全书一半以上的篇幅。不要以为"前三阶段读完就差不多了"——真正的深度在第四阶段。

一条重要的提醒

读完全部 28 章，不代表你会系统设计了。

这套笔记能给你的是模式库和别人踩过的坑。真正的能力来自：

  1. 在你自己的项目里做一次架构决策，并承担它的后果
  2. 线上出一次事故，然后复盘根因
  3. 把一个"能跑"的系统，改造成"能扛住 10 倍流量"的系统

所以，边读边动手。哪怕只是在本地用 Docker 起一个 Redis + MySQL，把笔记里的方案实现一遍，效果也远好于通读。
